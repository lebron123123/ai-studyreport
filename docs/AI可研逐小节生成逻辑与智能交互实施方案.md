# AI可研逐小节生成逻辑与智能交互实施方案

> 依据文件：`可研报告全逻辑梳理表_XX项目【出租-参考创景苑】(5).xlsx`
> 适用系统：可研报告工坊本地版
> 方案目标：把领导要求的“逐小节说明怎么写、需要什么材料、缺资料怎么办、怎样审核”变成可治理、可执行、可持续改进的系统能力。

## 一、结论先说

### 1. 不建议把整份Excel直接塞进现有“AI审核规则”

现有 `airules` 适合维护跨章节、跨项目通用的质量检查，例如“数字必须有来源”“市场结论必须有样本支撑”。本次Excel则描述了每一个小节的完整生产过程，包括：

- 这个小节写什么；
- 需要哪些项目资料、政策、市场数据或测算结果；
- 资料按什么顺序寻找；
- 采用分析生成、固定占位符、表格模板还是混合方式；
- 缺少数据时提示、阻断还是允许“待补”；
- 最后应该输出文字、表格、时间线、位置图或其他结构；
- 审核时检查什么。

它本质上是“逐小节生产作业指导书”，不是单纯审核规则。因此建议在后台新增独立的：

> **可研生成逻辑库**

生成逻辑库作为唯一业务源，同时向三个方向输出：

1. 向生成器提供写作步骤、数据需求、模板合同和缺数策略；
2. 向前台AI助手提供追问、检索、材料请求和候选稿生成能力；
3. 向审核器提供同一规则编号对应的检查项。

这样才能真正做到“按同一份标准生成，再按同一份标准审核”，又不会让生成逻辑与审核规则重复维护。

### 2. 后台负责治理，前台负责项目交互

确定采用“双层结构”：

- **后台**：管理员导入、修订、分类、发布生成逻辑，维护固定表格模板、来源要求、审核投影和版本。
- **前台AI可研对话**：围绕当前项目逐节执行已发布逻辑，自动找资料、列缺口、追问用户、生成候选内容并持续修改。

普通用户在前台的修改不会直接污染公司统一规则；被反复采用的改进可形成“逻辑优化建议草稿”，经管理员审核发布后，才影响以后所有项目。

### 3. 出租、出售、非居改保采用“公共基线＋类型覆盖”

不复制三套完全独立的181项逻辑。采用继承模式：

```text
通用可研逻辑 common
├─ 出租类 rent：覆盖租金、出租率、运营成本、长期现金流等差异项
├─ 出售类 sale：覆盖售价、销售节奏、销售费用、土地增值税等差异项
└─ 非居改保 gaibao：覆盖改造条件、租赁期限、改造成本、原物业约束等差异项
```

同一小节如果逻辑相同，只维护公共版本；存在差异时，仅保存该类型的覆盖字段。这样既避免重复，又能保证不同项目类型不被错误套用。

## 二、Excel核验结果

### 1. 表内可直接利用的结构

主表字段可映射为：

| Excel字段 | 系统字段 | 用途 |
|---|---|---|
| 序号 | `sourceNo` | 原始序号与溯源 |
| 一级章节 | `chapterPath[0]` | 一级章节定位 |
| 二级章节 | `chapterPath[1]` | 二级章节定位 |
| D列“税收” | `sectionTitle` | 实际内容明显是三级/具体小节，导入时不能按“税收”理解 |
| 四级要点 | `logicPointTitle` | 同一小节内的细分生产点 |
| 所需来源/数据源 | `requirements[]` | 材料与数据需求 |
| 写作逻辑 | `writingSteps[]` | 生成步骤和论证顺序 |
| 重要程度 | `importance` | 阻断、警告和普通提示依据 |
| 输出形式 | `outputContract` | 文字、表格、时间线、图等 |
| 备注 | `specialCase` | 项目特例，不能默认固化成全公司通用逻辑 |

### 2. 统计结果

- 主表共有137行机器可读取的逻辑记录，序号最大值为181；
- 原序号中有45个缺号，181重复一次；
- 重要程度：★★★重要54项、★★一般45项、★参考19项、空白19项；
- 需要外部资料或数据的记录约101项；
- 含表格、时间线、列表、示意图等结构化输出的记录至少37项；
- 数据来源涉及知识库46项、网上搜索42项、手工补充35项、平台/API约20项、其他章节或测算结果18项；
- 写作方法以分析法40项、罗列法29项、描述法15项为主，还包括时间线、供需分析、风险对策、市场调研等方法。

### 3. 导入前必须处理的数据质量问题

不能把Excel一键发布，必须先经过“导入预检”：

1. “章节统计概览”写合计181项，但主表实际只有137行记录；
2. 序号存在45个缺号，且181重复；
3. 使用说明称16章，但主表识别为14章加附表，章节口径需要人工确认；
4. 主表D列表头为“税收”，实际存放具体小节标题，应在导入映射时人工确认；
5. 19项重要程度为空，11项输出形式为空；
6. 概览表显示“重要项为0”，与主表54项★★★重要明显冲突；
7. 备注中的“高压线迁改、住房类型三次变更”等属于该案例特例，不能直接发布为所有出租项目的通用要求。

因此第一批实现必须包含：预检报告、字段映射、重复/缺号提示、案例特例识别和发布前人工确认。

## 三、推荐的后台信息架构

在后台新增一级入口：**可研生成逻辑库**。不塞进现有“AI审核规则、逻辑”长页面。

### 1. 页面分区

后台页面设置五个标签：

1. **逻辑目录**：按项目类型、章节、小节树查看；
2. **Excel导入**：上传出租/出售/非居改保逻辑表，预览映射与问题；
3. **表格与占位符模板**：维护固定表头、行项、公式来源和缺数显示；
4. **版本与发布**：草稿、待审核、已发布、已归档、版本差异；
5. **优化建议**：接收前台交互中形成的规则改进候选，管理员决定是否吸收。

### 2. 单条生成逻辑的数据结构

```json
{
  "id": "RL-RENT-001",
  "projectType": "rent",
  "inheritFrom": "RL-COMMON-001",
  "chapterKey": "chapter_01",
  "sectionKey": "1.1.6",
  "chapterPath": ["第一章 总论", "1.1 项目背景", "1.1.6 主要前提条件"],
  "logicPointTitle": "户型配比",
  "importance": "critical",
  "generationMode": "hybrid",
  "requirements": [],
  "writingSteps": [],
  "outputContract": {},
  "missingPolicy": {},
  "auditProjection": [],
  "evidenceRefs": [],
  "status": "published",
  "version": 1
}
```

### 3. 生成模式必须明确区分

| 模式 | 适用内容 | 系统行为 |
|---|---|---|
| `ai_analysis` 智能分析 | 必要性、市场分析、SWOT、风险结论 | AI按已发布逻辑和真实证据生成 |
| `fixed_template` 固定模板 | 固定表格、附表、固定政策列表 | 使用模板合同，只回填允许变化的槽位 |
| `hybrid` 混合生成 | 户型配比、租金分析、投资估算说明 | 固定结构＋AI解释＋真实数字回填 |
| `derived` 确定性结果 | 财务指标、测算表、工期投资计划 | 只读取白箱引擎结果，AI不能改数字 |
| `manual_only` 人工专属 | 政府意见、未公开会议纪要、特定历史事项 | 不允许AI猜测，只能请求用户提供 |

### 4. 材料需求采用结构化清单

每个 `requirements[]` 至少包含：

- `name`：需要什么，例如“市政府用地批复”；
- `kind`：政策/项目批复/测算字段/市场数据/图纸/会议纪要；
- `requiredLevel`：必须、建议、参考；
- `sourceOrder`：项目已上传资料 → 正式资料台账 → RAG/Wiki → Provider/联网检索 → 询问用户；
- `acceptance`：文件名、发布日期、适用区域、统计期、样本量等合格条件；
- `fieldMappings`：需要从材料中提取哪些字段；
- `allowWeb`：能否联网寻找；
- `manualOnly`：是否必须由用户/业务部门提供；
- `evidenceRequired`：正文是否必须带来源；
- `missingAction`：阻断、警告占位、允许省略。

## 四、前台智能交互如何运行

前台不新增一个孤立的复杂表单，而是在现有“AI可研生成”对话中增加“逐小节编制助手”。

### 1. 项目开始时：先生成材料需求地图

用户选择出租类并确认项目基本信息后，系统加载：

```text
公共逻辑已发布版本
＋出租类覆盖逻辑已发布版本
＋当前报告大纲
＝本项目逐小节任务图
```

系统展示：

- 已具备材料；
- 可从知识库自动命中的资料；
- 可从联网/Provider查找的数据；
- 必须让用户上传的内部材料；
- 因缺少资料暂不能形成正式结论的小节。

### 2. 每个小节采用六步闭环

1. **读取逻辑**：确认本节生成模式、写作步骤、输出合同；
2. **盘点证据**：检查项目附件、正式资料、RAG、Wiki、测算结果；
3. **自动补查**：按规则允许的范围查知识库、Provider或互联网；
4. **智能追问**：仅询问仍缺失且确实需要人工提供的内容；
5. **形成候选稿**：生成文字、固定表格或混合内容，不直接覆盖已确认正文；
6. **接受/修改/退回**：用户确认后成为当前版本，修改意见进入项目记忆。

### 3. 交互示例：固定表格

用户进入“户型配比”小节后，AI不是直接自由生成，而是提示：

> 本节要求输出“户型配比表”。当前逻辑库尚未发布表格合同。请确认列项是否采用：户型、建筑面积、套数、套数占比、建筑面积占比、目标客群、确定依据。确认后本项目先按该模板生成，同时形成一条“公司模板优化建议”，等待管理员审核。

管理员审核通过后，后续出租项目直接复用该表格合同。

### 4. 交互示例：资料不足

> “投资决策背景”要求项目历史会议纪要和用地批复。知识库只命中了公开政策，无法证明本项目历史。请上传会议纪要/用地批复，或选择“先生成待补框架”。

如果用户选择待补框架，页面显示专用缺口块，不把AI猜测写成正式事实。

### 5. 缺少数据的页面表现

设置四级状态：

- **绿色：已满足**——材料、统计期和来源均合格；
- **蓝色：自动补齐**——来自RAG、正式台账、Provider或确定性测算；
- **黄色：可继续但待补**——输出框架和占位符，正式签发前必须替换；
- **红色：阻断**——核心结论缺少必需依据，不能生成正式稿或签发。

正文中的缺口使用结构化块，而不是普通文字：

```text
【资料缺口提示｜草稿标记】
缺少：项目用地批复中的规划指标。
影响：本节只能展示表格框架，不能确认容积率与计容建筑面积。
补充方式：上传批复文件，或从正式资料台账选择对应文件。
```

草稿导出可选择保留黄色提示；正式签发导出若仍有红色缺口则必须阻断。

## 五、生成逻辑、审核规则、Wiki/RAG的关系

### 1. 各模块只负责一件事

| 模块 | 责任 | 不负责 |
|---|---|---|
| 可研生成逻辑库 | 本节怎么生产、需要什么、输出什么、缺数怎么办 | 不保存原始政策全文 |
| AI审核规则 `airules` | 跨章节通用质量规则 | 不描述完整生产流程 |
| 测算审核标准 `calcstd` | 数字、公式、阈值和分档 | 不生成市场论证 |
| Wiki | 解释为什么这样规定、沉淀公司经验 | 不直接扣分 |
| RAG/正式资料台账 | 提供事实、政策、项目材料和来源 | 不决定写作顺序 |
| 黄金范例 | 提供优秀表达与结构参考 | 不作为当前项目事实 |

### 2. 审核不复制生成逻辑，而是读取“审核投影”

每条生成逻辑可配置 `auditProjection[]`，例如：

```json
[
  {"check":"是否说明样本范围和统计期","severity":"warn"},
  {"check":"租金结论是否引用真实调研数据","severity":"block"},
  {"check":"表格列项是否符合已发布模板合同","severity":"warn"}
]
```

生成器和审核器都引用同一个规则编号 `RL-RENT-xxx`。审核结果继续沿用现有展示路径：

> 检查了什么 → 依据哪条规则 → 为什么这么规定 → 应该怎样修改

现有 `airules`、`calcstd` 继续保留，分别叠加通用质量检查和数字硬规则，不与逐小节逻辑重复建档。

## 六、“越来越智能”怎样实现且不失控

### 1. 三层记忆分开

1. **项目记忆**：当前项目已提供什么材料、用户确认过什么、哪个小节锁定；
2. **个人偏好**：用户习惯的表达、表格密度、篇幅等，可随时清除；
3. **公司逻辑**：所有项目共用，必须后台审核发布，不允许AI自动改写。

### 2. 用户交互不会直接修改公司规则

当用户说“以后这张表都按这个结构”时，系统执行两件事：

- 当前项目立即保存为候选模板并使用；
- 生成一条“逻辑优化建议”，包含原规则、修改建议、示例、适用项目类型和影响小节。

只有管理员在后台点击“接受并形成新版本”，才进入公司统一逻辑库。

### 3. AgentCore新增的业务工具

在现有 `AgentCore` 上注册以下工具，不另造一套智能体框架：

- `get_section_generation_logic`：读取当前小节已发布逻辑；
- `check_section_requirements`：输出已满足、缺失和不合格资料；
- `search_section_evidence`：按允许范围检索RAG、正式资料、Provider/网络；
- `request_section_material`：生成明确的上传请求与验收条件；
- `preview_section_generation`：生成候选内容，不覆盖正式正文；
- `validate_output_contract`：检查固定表格、行列、数字来源；
- `propose_generation_logic_improvement`：形成后台待审核建议；
- `get_logic_version_diff`：解释新旧逻辑对报告的影响。

所有写操作继续采用现有“候选稿 → 接受/拒绝/撤销”的人工闸门。

## 七、建议的数据表与接口

### 1. 数据表

- `report_logic_rules`：规则主表、类型、章节定位、状态和版本；
- `report_logic_versions`：每次发布的完整快照；
- `report_logic_templates`：表格/时间线/列表等输出合同；
- `report_logic_requirements`：资料与数据需求；
- `report_logic_suggestions`：前台产生、待管理员审核的优化建议；
- `project_section_tasks`：项目逐节执行状态、缺口和当前规则版本；
- `project_section_evidence`：小节实际使用的材料和单元格级来源。

数据库迁移必须幂等，旧项目没有这些字段时仍按当前生成方式运行。

### 2. 接口

- `/api/reportlogic`：列表、详情、保存草稿、发布、归档、版本差异；
- `/api/reportlogic-import`：Excel预检、字段映射、导入草稿；
- `/api/reportlogic-execute`：计算单节材料状态和生成任务；
- `/api/reportlogic-suggestions`：提交、审核、采纳优化建议。

前台普通用户只能读取已发布逻辑和提交建议；管理员才能修改、发布或归档。

## 八、与现有代码的接入位置

### 后台

- `admin.html`：新增“可研生成逻辑库”导航与管理页面；
- 新增 `report-logic-admin.js/css`：章节树、Excel导入预检、版本和模板合同；
- 不继续把大量代码堆进 `admin.html`，避免后台单文件进一步膨胀。

### 生成

- `report.js`：在 `generateSection()` 前加载小节逻辑；将 `stdRetrieve()` 扩展为“通用审核标准＋逐小节生成逻辑＋测算标准”；
- 固定表格不交给模型自由拼接，而由输出合同渲染；
- `prov` 溯源记录新增 `logicRuleId/logicVersion/requirementStatus`。

### 对话与Agent

- `aireport.js`：在项目信息确认后增加材料需求地图；报告生成后支持按小节继续问答；
- `agent-core.js`：框架本身不用改，只注册新的可研业务工具；
- 项目会话存档继续复用 `aireport_project_sessions`。

### 审核

- `review.js`：读取同一条生成逻辑的 `auditProjection`，检查资料满足情况和输出合同；
- 继续叠加 `airules` 与 `calcstd`；
- 红色阻断项未解决时，不允许“确认签发”。

## 九、实施顺序

### 第一批：Excel预检与逻辑库底座

1. 建立数据库表和API；
2. 新增后台“可研生成逻辑库”；
3. 支持出租Excel上传、字段映射、问题清单和草稿导入；
4. 将项目特例与通用逻辑分开；
5. 发布前显示章节数、记录数、缺号、重复项、空字段和版本差异。

**验收**：出租表只能作为草稿导入；未解决数据质量问题前不能发布。

### 第二批：逐小节生成接线

1. `report.js` 按项目类型和章节精确命中逻辑；
2. 支持五种生成模式；
3. 固定表格使用结构化合同；
4. 生成结果记录规则版本和证据来源；
5. 旧项目保持兼容。

**验收**：抽取至少10个代表性小节，分别验证纯文字、分析、固定表格、白箱测算和人工专属模式。

### 第三批：前台材料需求地图与智能追问

1. 对话中显示小节材料状态；
2. 自动查询正式资料、RAG/Wiki、测算结果和Provider；
3. 找不到时精确要求用户上传，不做泛泛追问；
4. 支持待补框架、阻断和继续生成；
5. 用户补材料后只更新受影响小节。

**验收**：用“有完整资料、缺非关键资料、缺核心资料”三种项目场景进行端到端测试。

### 第四批：生成—审核同源闭环

1. 自动生成审核投影；
2. 审核结果显示规则编号与版本；
3. 检查固定表格合同、数字来源和材料缺口；
4. 红色缺口阻断签发；
5. 数据或逻辑版本变化触发影响预演与选择性更新。

### 第五批：持续学习与多类型扩展

1. 前台修改沉淀为优化建议，不直接改全局规则；
2. 管理员审核后形成新版本；
3. 导入出售类和非居改保Excel；
4. 自动比对公共逻辑与类型差异；
5. 建立三类项目的回归样例集。

## 十、测试策略

每批按项目 `AGENTS.md` 的最小变更原则验证：

- Excel导入：表头变化、合并单元格、空值、重复序号、错误章节、重复导入；
- 版本治理：草稿不生效、发布后生效、归档后不再用于新项目、旧项目保留原版本；
- 精确匹配：出租逻辑不能误用于出售/非居改保；公共逻辑能被三类继承；
- 材料检索：正式资料优先于普通RAG，过期政策不得作为现行依据；
- 缺数策略：黄色提示、红色阻断、占位表格均按规则工作；
- 输出合同：固定表头/行项不被AI改写，数字必须来自测算或有溯源的数据；
- 交互闭环：追问、上传、候选稿、接受、拒绝、撤销、刷新恢复；
- 审核闭环：生成规则编号与审核命中规则一致；
- 旧功能回归：现有AI可研参数推荐、测算、逐章生成、复核、Word/Excel导出不受影响。

## 十一、最终用户体验

最终用户不需要理解后台181项逻辑。用户只会看到：

1. 选择出租/出售/非居改保并描述项目；
2. 系统告诉他当前材料完整度，以及真正还缺什么；
3. 能自动查到的资料由系统查，必须内部提供的才向用户索取；
4. 每个小节按已发布逻辑生成，固定内容按模板、分析内容由AI、数字来自白箱引擎；
5. 缺资料的位置明确提示，不编造；
6. 用户可以围绕某一小节持续对话修改；
7. 被反复认可的修改经过管理员审核后，成为以后项目的新标准；
8. 审核阶段按生成时的同一规则逐项检查，并能追溯规则版本、资料和数字来源。

## 十二、最终建议

本轮应先实施第一批，不应马上把137行记录直接写入现有 `airules`。正确起点是：

> **先建立“可研生成逻辑库＋Excel预检导入＋草稿/发布治理”，把这份出租表安全、结构化地导入后台；确认章节和数据问题后，再接入前台逐小节生成。**

这是后续出售类、非居改保能够低成本扩展，同时保证生成和审核一致的关键底座。
