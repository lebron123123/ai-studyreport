## 1. 要解决的问题及采用的方法

1. 将参考报告的商务分析写法提炼为可维护规则，不把参考报告的项目事实、出租模式或整篇正文套到所有项目。
2. 保留原章节结构和业务分析逻辑，在其上增加“怎么组织段落、怎么解释表格、哪些话不应写”的共享标准。
3. 将散落正文的待补要求变成有身份、有主位置、有状态、有资料版本的台账；不能仅按相似文字合并，更不能以删红字代替补资料。
4. 分开“尚未核验”“确认缺失”“人工核验完成”和“正式成果批准”，避免红字泛滥和假通过。
5. 经生成契约、服务端权威规则和冻结快照贯通；规则升级不自动改写原稿和历史成果。

## 4. 行文与业务逻辑分工

业务规则继续决定分析什么：章节职责、事实、经营口径、表格、指标和数据需求不被替换。新标准决定怎样表达：直接陈述差异、原因、影响和项目判断，避免“本节将……”“为后文奠定基础”等写作过程说明；保留合理业务背景、因果、方法边界及不确定性，不能见到“因为/因此”就删除。

每段承担任务，段间递进，不机械凑四段。表格保留明细，正文解释驱动因素和含义，不逐格复述。核实事实、材料陈述、假设和待确认事项分开；不得靠文风补出数字。

九类角色：依据、项目说明、市场、需求、定价、财务、风险、结论、实施安排。可选槽位不要求全部使用，不增加原预算。依据类继续仅列文件及核实的文号、机关、日期，不解读政策或臆造元数据；既有 `basisCatalog` 管理其完整性，不重复制造正文缺口。

确定性检查仅定位明确元叙述，返回段落、行号、原文和警告，不以正则删旧文。语义深审只接受限定 JSON 及对应段落精确引用；格式、定位错误或项目/正文变化使结果失效。可提示重复、弱分析、论据不足、逻辑断裂、表文重复，但保留 `factsVerified:false`。修改仍走候选及人工接受。

## 5. 台账：减少重复，不减少责任

### 5.1 身份和归属

明确配置事实字段的需求可细化到字段。身份绑定项目、情景、对象、地域、时期、字段及来源版本；相似文字不等于同一事实。默认来源/统计期等元信息字典不机械展开为每字段一条红缺失，未明确细分仍保留需求级复核项。

每项有一个主小节及相关小节。完整说明在主位置，其他相关处只在影响判断时保留简短引用或决策边界；无法区分的冲突报错，不静默合并。

### 5.2 状态和显示

| 状态 | 含义与正文 | 是否已齐 |
| --- | --- | --- |
| `unverified`、`unlocated` | 尚未核验/定位；主位置简短非红边界，不宣称确认缺失 | 否；关键项仍阻止正式签发 |
| `missing`、`partial`、`conflict`、`parse-failed` | 缺失、不完整、冲突、解析失败；主位置完整红色 `【待补：…】` 一次 | 否 |
| `satisfied` | 当前身份/资料/需求版本匹配且核验有效 | 仅关闭该项，不等于全篇事实认证 |
| `not-applicable` | 明确人工理由及有效后台收据 | 仅关闭该项，AI 不能自行取消需求 |

旧红标只是迁移复核线索，不自动删改。未匹配需求的小节不能按零缺口冒充覆盖完整。资料来源绑定规则与覆盖、项目事实、参数、实际材料内容、目录及类型/情景；服务端核验完整内容强哈希，不仅信任材料自报哈希。实际内容、身份、版本变化使旧确认失效，无关上传时间不应失效。

## 6. 后台人工确认收据

`confirmGap` / `verifyGaps` 不等于前端修改 `status`：

1. 正式项目校验编辑权限、所有者口径及数据库版本；研究校验研究/轮次及版本。事务锁和版本比较拒绝晚到写入。
2. 确认已齐需唯一真实已保存材料、实际存在的精确原文和定位、人工理由；无 ID 历史材料有稳定身份，重复歧义拒绝。
3. 不适用须明确人工理由，AI 建议不能直接批准。
4. 用环境 `SESSION_SECRET` 域隔离 HMAC-SHA256，绑定完整来源 SHA256、项目/轮次、字段、需求及版本；密钥不落源码/前端/收据。
5. 审计事件 `report.gap.human-confirmed` 保留。返回仍需保存的台账与收据，`formalApproval:false`；不自动覆盖原文。
6. 服务端重新验签，不信任原始 `trustedApprovals`、请求布尔或手改状态。收据撤回、资料变化、密钥轮换使依赖候选失效。

精确引用只证明已保存材料确有该文字，收据证明特定身份在该版本确认；不代表系统独立证实材料外部真实性、效力或结论。

## 7. 正式门禁与历史兼容

没有台账及相关服务端历史的旧项目默认 schema 3。拥有 `reportGapRegistry` 属性者用 schema 4，即使值空、无效或未应用也不能绕过。

schema 4 冻结正文、台账及服务端规则/核验上下文；正式检查重新派生，不直接信任可编辑“通过”缓存。关键未解决、来源过期、伪造满足、丢记录、降低关键级别、主位置错误、未匹配章节、未应用均阻止签发，即使正文无红字。

已有 schema 4 历史或后台确认审计后，删除整个台账也不得降级。只读历史，无新增迁移：新冻结要求恢复核查；旧 pending 3 不能直接批准，须重冻；旧稿不能标为当前。历史已批准 3 仍可下载/历史引用，schema 1–3 哈希不改。

“最近十二个月/最近三年”等程序核验范围说明只在完整结构化门禁通过、冻结来源有效、主位置逐字匹配且仅出现一次时，在数值检查专用副本替换。原正文/哈希不变，其他必需/禁止/红标/表格/引用检查仍读完整原文。变体、重复、注释隐藏、红标、额外经营数字无豁免；另加无依据的“运营期限为12年”仍阻止。

保留作者与复核人分离、权限、快照完整性、版本比较、事实及 Word 排版复核确认。台账通过不等于审签。历史恢复不回退当前事实，台账重新核对。

## 10. 明确边界

1. **真实项目未接受重写。** 未自动替换税务局、龙岗或其他项目，未人工逐节接受新文风候选，原文保留。
2. **隔离浏览器不等于真实端到端。** 真实 index/脚本/DOM 搭配 API/AI/持久化 fixture，只证明隔离页面行为；不能证明真实登录、数据库、外部模型、正式项目接收全链路。须另记证据。
3. **D1 不支持此事务闭环。** 收据及持久化生成依赖 `_transaction` 和版本锁；不具备则失败。本轮真实闭环为 PostgreSQL，不能称 D1/纯静态 Cloudflare 通过。缺 `SESSION_SECRET` 不降级放行。
4. **规则/语义审查不是事实裁判。** 保守模式覆盖有限，模型深审仍需人工判断，签名/引用/测试不是事实真实的证明。
5. **不承诺 95% 或完美文风。** 无多项目盲评、长期生产统计及独立专业复核，不能从测试数推算准确率。
6. **不新增页数保证。** 既有预算/排版门禁不变，税务局/龙岗新文风全稿尚无逐页 Word 验收，不同字体及 Word/WPS 重排边界仍在。
7. **未发布。** 最终本地全量与同进程运行确认已完成；独立生产环境、备份恢复和真实项目业务验收仍未覆盖，本地实现不等于线上生效。

在用户选择并授权的项目副本，先核对发布规则和台账，再生成代表性小节候选（市场、财务、风险、结论、依据），人工对照事实、文风、表格和重复说明；通过后扩大到全篇。保留候选差异、资料确认、正式审签和实际排版证据，隔离 fixture 不能代替这些步骤。

## 12. 用户操作入口

1. 报告页面“全篇要求”内新增“专业成稿标准”，提供“检查全篇行文 / 小节深审”和“项目待补总台账”。
2. 管理员编辑全篇要求时可维护通用行文与分职责规则，发布当前类型新版本；不隐式发布其他类型，也不替换原稿。
3. 台账先核对需求、对象、时间地域与资料，再显式应用；AI 只给建议。确认已齐需保存材料中的准确原文和定位，确认不适用需人工理由；保存/验签失败不得算已完成。
4. 对旧稿生成候选并比较后接受。原章节、表格、公式和正式历史保留，不靠删字、删表或取消关键事项减少红字。
