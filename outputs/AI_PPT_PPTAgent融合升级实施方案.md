# AI PPT × PPTAgent 融合升级实施方案

## 一、先给结论

当前不建议把 `icip-cas/PPTAgent` 整套代码直接替换进现有系统，建议采用“保留现有业务底座，吸收 PPTAgent 生成内核”的融合路线。

原因很简单：

- 现有系统已经具备项目资料解析、数字溯源、可研与测算数据连接、项目版本、Design IR 所见即所得、原生图表、PPTX 导出和本地部署能力。这些是 PPTAgent 不理解的公司业务资产，不能丢。
- PPTAgent 的优势不只是多几个版式，而是完整采用了“参考模板学习—大纲规划—版式检索—内容写入—逐页检查—失败重试”的工作流。
- PPTAgent 是 MIT 许可证，可以依法使用、修改和再发布，但需要保留其版权和许可声明。
- PPTAgent 官方说明当前不直接支持 Windows，推荐 WSL 或 Docker；它还依赖 Python 3.11、Playwright、Docker、视觉模型、文档解析和多个服务。整套搬入会显著增加本地部署、50人并发和后续服务器运维复杂度。

因此最优方案不是“再抄一个 Git 项目的界面”，也不是“推倒现有代码重来”，而是把 PPTAgent 最有价值的五个机制接入现有 AgentCore 和 PPT 工作区：

1. 参考 PPT 自动学习；
2. 先生成并确认可编辑大纲；
3. 根据内容形态检索真实模板页面；
4. 逐页生成、逐页反思和返修；
5. 内容、设计、连贯性三维质检。

## 二、为什么吸收了四个 Git 项目，页面仍然不够高级

目前的问题不是颜色，也不只是卡片数量，而是生成层级仍然偏浅。

现有链路大致是：

> 一次 AI 调用生成故事线和逐页内容 → 从固定组件/配方中选一个 → Design IR 渲染 → 导出。

这条链路已经比最初稳定很多，但仍有五个结构性限制：

### 1. 学到的是“组件外观”，没有学到“模板构图语法”

当前已有约 24 个组件定义、18 个整页配方和一套 160 页模板来源映射，但多数配方仍由代码手工描述。系统知道“这是时间轴、这是双栏”，却不知道参考页为什么这样安排主视觉、标题、数字、图片、辅助信息和留白。

### 2. 一次性生成，缺少逐页设计循环

现在 AI 主要一次输出整套 JSON。PPTAgent 则把每页作为独立任务：先选版式，再按版式槽位生成内容，再执行修改动作，失败后重试。DeepPresenter 路径还会逐页渲染并调用检查工具，未通过就继续修改。

### 3. 模板只是颜色主题，不是真正的页面能力库

用户选择“安居蓝、政务简洁、高级商务蓝”后，当前主要改变配色、字体和有限构图。成熟产品里的“模板”通常包含几十种可被检索的真实页面，例如封面、目录、章节页、数据页、对比页、时间轴、组织关系页、结论页等。

### 4. 图片不是一等公民

当前已经能解析和匹配项目图片，但还没有形成“上传图片包—图片理解—宽高比识别—图片去重—图片槽位规划—缺图时生成图片”的完整链路。没有图片、地图、效果图、图标和装饰素材，页面只能依靠文本框与几何图形，自然容易显得空和呆板。

### 5. 版式分类是技术分类，不是用户任务分类

用户不关心 `three-cards`、`two-column` 这些代码名。用户真正关心的是：这一页是“结论”“数据证据”“方案对比”“工作计划”“风险应对”还是“请求决策”。模板和页面候选应围绕沟通任务分类。

## 三、PPTAgent 真正值得吸收的核心

根据 PPTAgent 官方仓库和论文，其模板路径分为两个阶段：

### 阶段 A：模板归纳

- 将参考 PPT 渲染成图片；
- 识别封面、目录、章节、结束页等功能页；
- 根据页面布局、内容类型和视觉相似度对页面聚类；
- 为每一类页面提取内容槽位和容量约束；
- 形成可供后续检索的 `slide_induction` 模板画像。

### 阶段 B：生成

- Planner 根据材料结构形成大纲；
- Content Organizer 提取当前页面需要的材料；
- Layout Selector 根据文字长度、元素数量、图片相关性和整套大纲选择最佳页面；
- Editor 把内容映射到模板槽位；
- Coder 生成替换文字、图片和元素的编辑动作；
- 执行、验证，失败则根据反馈重试。

这比“给每类页面写一个固定 JS 渲染函数”更接近人类做 PPT 的过程。

PPTAgent/DeepPresenter 目前还采用双路线：

- 模板路线：学习并复用真实 PPT 页面，适合公司固定模板和正式汇报；
- 自由设计路线：根据内容逐页生成 HTML/CSS，并逐页检查，适合没有模板或强调视觉创意的场景。

我们的系统也应采用类似双路线，而不是强迫所有项目使用同一种生成方式。

## 四、目标产品流程

建议把 AI PPT 前台改为九步闭环。

### 第 1 步：输入任务和材料

用户可输入主题，也可上传 Word、PDF、Excel、Markdown、图片和既有 PPT。

同时明确：

- 汇报对象；
- 汇报目的；
- 目标页数；
- 是否正式决策汇报；
- 是否优先使用项目图片；
- 是否必须使用部门模板。

### 第 2 步：选择设计来源

把“模板”拆成三个清晰入口：

1. 自由风格：系统根据内容形成设计方向；
2. 官方模板库：管理员审核并发布的部门模板；
3. 上传参考 PPT：用户上传自己的 PPT，系统分析其页面，不允许直接修改公共模板。

模板图库按使用场景分类，而不是按代码版式分类：

- 领导决策；
- 项目汇报；
- 财务测算；
- 工作总结；
- 战略咨询；
- 宣传展示；
- 学术研究。

模板卡片显示封面缩略图、适用场景、颜色、页型数量和来源，不只显示模板名称。

### 第 3 步：形成“汇报简报”

AI 先生成一张简报卡，而不是立刻生成 PPT：

- 一句话核心结论；
- 听众最关心的问题；
- 汇报要推动的决策；
- 叙事方式；
- 建议章节数与页数；
- 建议视觉方向；
- 材料缺口。

用户可以修改后再进入大纲。

### 第 4 步：生成可编辑大纲

大纲必须成为独立步骤和明确的确认门槛。当前“逐页方案”已经存在，但埋在生成后的编辑区，应该前移。

大纲编辑器支持：

- 修改章节名和每页标题；
- 拖动排序；
- 增删页面；
- 合并或拆分页面；
- 标记“必须保留”“需要图片”“需要图表”“需要项目数据”；
- 单独重新生成某个章节；
- 显示每页的任务、结论、材料来源和建议页型；
- 点击“确认大纲并开始设计”后才进入逐页生成。

推荐的大纲结构不是“标题列表”，而是：

```json
{
  "section": "财务与实施判断",
  "slides": [{
    "title": "项目收益对关键租金参数高度敏感",
    "job": "证明核心参数的重要性",
    "takeaway": "租金是最需要人工确认的参数",
    "contentShape": "chart+insight",
    "requiredEvidence": ["测算结果", "敏感性曲线"],
    "imageNeed": "none",
    "locked": false
  }]
}
```

### 第 5 步：逐页检索真实页面

每页不直接选择一个固定 JS 布局，而是先检索 3 个候选页面。

候选评分至少包括：

- 页面任务匹配度；
- 文字、数字、表格、图片的元素数量匹配度；
- 内容容量匹配度；
- 图片比例匹配度；
- 与前后页面的节奏差异；
- 与选定模板的风格一致性；
- 是否包含需要的原生图表或表格槽位。

系统可以默认选择第一名，同时允许用户在缩略图中换成第二、第三候选。

### 第 6 步：双引擎生成

#### A. 真模板复用引擎

适用于官方模板或用户上传模板：复制真实模板页，替换槽位内容，保留原来的图片蒙版、装饰、字体层级、对齐和组合关系。

#### B. 自由设计引擎

适用于自由风格：继续使用现有 Design IR，但升级为“页面设计程序”，让 AI 输出更丰富的元素树，而不只是选择 18 个固定配方。

每页建议形成：

- 1 个视觉焦点；
- 2—4 个主要信息组；
- 1 个图、表、图片或关系图；
- 5—12 个辅助视觉元素；
- 明确的阅读路径（Z 型、F 型、对角、中心辐射、海报式等）。

这里强调“信息层次丰富”，不是为了填满而堆元素。

### 第 7 步：图片和素材能力

这部分完全可以实现，分为两层。

第一层先做本地能力：

- 上传 JPG、PNG、SVG、项目效果图、区位图和照片包；
- 自动提取尺寸、比例、文件来源和重复图片；
- 对图片生成简短语义标签；
- 根据页面任务匹配横图、竖图、背景图或小图；
- 用户可在某页点击“换图”“裁剪方式”“设为背景”“锁定图片”。

第二层预留图片生成 Provider：

- 本地 Stable Diffusion/Flux；
- 公司允许的图像生成服务；
- 未来其他模型接口。

AI 生成图片必须标识“AI生成”、提示词、模型和版本，不能与项目正式照片混淆。

### 第 8 步：逐页反思和整套质检

将现有 QA 升级为类似 PPTEval 的三层体系：

1. 内容：结论是否有证据、数字是否可追溯、标题是否表达判断；
2. 设计：布局、密度、层级、图片质量、对齐、对比度、溢出；
3. 连贯性：章节顺序、前后页面关系、重复版式、重复内容、结论是否闭环。

生成时每一页执行：

> 渲染预览 → 规则检查 → 视觉模型检查（可选）→ 生成修改建议 → 自动返修 → 再检查。

没有视觉模型时使用本地几何与规则检查；接入视觉模型后再增强审美判断，不让云端接口成为基础功能的硬依赖。

### 第 9 步：对话式改稿

对话不只回答问题，而是具备明确 PPT 工具：

- “第 5 页太空，增加一个关系图”；
- “这一页改成左右图文版”；
- “把第 3—5 页压缩成两页”；
- “全部换成我刚上传的项目图片”；
- “保留数据，只换一个更稳重的版式”；
- “按董事会汇报方式重写大纲”；
- “撤销刚才对第 7 页的修改”。

每次修改先给差异预览，用户接受后形成新版本。

## 五、对现有代码的落地映射

| 能力 | 保留/升级位置 | 建议新增模块 |
|---|---|---|
| 材料解析和数字溯源 | `ppt-evidence.js` | 增加 PPT、图片包的结构化解析 |
| 项目与版本 | `functions/api/pptprojects.js`、`ppt-workspace.js` | 增加生成任务状态和大纲版本 |
| 大纲与故事线 | `ppt-core.js` | `ppt-outline-editor.js`、`ppt-story-director.js` |
| 模板图库 | 目前仅有模板下拉框 | `ppt-template-gallery.js`、`functions/api/ppttemplates.js` |
| 模板自动学习 | 目前只有160页人工盘点 | `local-server/ppt-template-inductor.js` |
| 页面检索 | `ppt-component-registry.js`、`ppt-layout-recipes.js` | `ppt-layout-retriever.js`，返回Top 3候选页 |
| 页面生成 | `ppt-design-ir.js`、`local-server/ppt-native-template.js` | `ppt-page-director.js`，统一两条生成路线 |
| 图片素材 | `ppt-asset-layer.js` | 增加图片理解、裁剪策略和Provider接口 |
| 视觉检查 | `ppt-visual-qa.js`、`ppt-qc.js` | 增加连贯性评价和可选视觉模型评价 |

| 导出 | `local-server/ppt-export.js` | 继续复用共同 Design IR，保持预览导出一致 |

## 六、分五批实施

### 第一批：先把交互流程做对

- 新建 PPT 首页改为任务输入 + 模板图库；
- 支持自由风格、官方模板、上传参考 PPT；
- 增加“汇报简报”；
- 增加独立可编辑大纲和确认按钮；
- 大纲确认前不生成完整页面。

验收：用户能够完成“上传材料—选择模板—修改大纲—确认生成”的完整流程。

### 第二批：模板归纳和页面检索

- 对上传 PPT 一次性渲染全部页面；
- 提取设计令牌、功能页、内容槽位和页面容量；
- 生成模板画像和页面缩略图库；
- 每页返回 Top 3 候选真实模板页；
- 模板未变化时不重复全量分析，只做文件指纹和增量检测。

验收：同一份材料使用不同模板时，页面不仅换颜色，而且真正换成不同模板里的构图。

### 第三批：逐页生成和素材能力

- 模板页槽位替换；
- Design IR 自由页面元素树升级；
- 图片包上传、语义匹配、裁剪和换图；
- 图表、表格、项目图片成为页面一等元素；
- 每页独立生成，可单页重做。

验收：普通内容页不再只有两三个文本框；至少包含明确焦点、信息组和视觉证据。

### 第四批：逐页反思和对话改稿

- 内容、设计、连贯性三维评价；
- 单页渲染—检查—返修循环；
- 对话调用重排版、换图、拆页、合页、重写大纲等工具；
- 差异预览、接受、拒绝、撤销和版本恢复。

验收：用户指出“第5页太空/不好看”时，系统能定位页面、说明问题、给出候选并只更新该页。

### 第五批：生产化和可扩展 Provider

- 模板审核、发布、停用和权限；
- 图片生成 Provider；
- 任务队列、并发隔离和失败恢复；
- 模板/模型/提示词版本记录；
- 视觉质量统计和用户选择反馈；
- 可选把 PPTAgent/DeepPresenter 作为独立 Python 容器 Provider 接入，而不是侵入主系统。

验收：服务器部署后，多用户生成任务互不影响，所有结果可追踪、可恢复。

## 七、哪些代码可以借，哪些不建议直接搬

### 建议吸收

- 两阶段“模板归纳 + 生成”思想；
- 功能页识别和内容页聚类；
- 内容槽位与容量 Schema；
- Planner、Layout Selector、Editor 的职责拆分；
- 每页执行动作、失败反馈和重试；
- 模板路线与自由路线并存；
- Content / Design / Coherence 三维评价。

### 不建议直接搬入主程序

- 整套 Python/Gradio WebUI；
- 强依赖 WSL、Docker 和外部视觉模型的运行环境；
- 与现有 AgentCore、PostgreSQL、RAG、用户权限重复的会话和服务层；
- 直接让模型生成任意代码并在主 Node 进程执行；
- 用其模板管理替换现有项目、版本和审查体系。

PPTAgent 可以在第五批成为一个独立、受限的生成 Provider；现阶段先把其核心方法用现有技术栈重建，风险更小，集成更深。

## 八、最终形态

最终用户看到的不是一个“版式下拉框”，而是类似成熟 AI PPT 产品的工作台：

1. 输入主题或上传材料；
2. 选择自由风格、官方模板或上传参考 PPT；
3. 上传项目图片；
4. 查看并修改汇报简报；
5. 查看、拖动和修改大纲；
6. 确认后逐页生成；
7. 每页可切换候选构图、换图、锁定或对话修改；
8. 系统自动进行内容、设计和连贯性质检；
9. 预览与导出保持一致；
10. 所有数据、图片、模板和修改历史均可追溯。

这条路线能保留现有系统在可研、测算、知识库和数据溯源上的优势，同时真正补上 PPTAgent 最强的“从参考模板学习并逐页生成”能力。
