# AI PPT 160页组件库与 CyberPPT 深化实施方案

> 日期：2026-08-17  
> 适用项目：`ai-studyreport-local`（本地部署版）  
> 本文目标：在不破坏财务测算、可研生成、知识库等既有功能的前提下，把当前 AI PPT 从“能生成、能导出”提升为“能读材料、会讲故事、会选版式、可追溯、可编辑、可质检”的稳定产品。

## 一、先给结论

这次不应把旧 `addition` 代码整包恢复，也不应把 160 页模板逐页照搬进渲染器。

最合适的路线是：

1. 保留当前已经稳定的材料解析、证据包、AI 逐页方案、可编辑 PPTX 导出和视觉 QA。
2. 对 160 页模板做一次全量结构扫描与版式聚类，提炼“设计令牌、基础组件、组合版式、整页配方”四层资产。
3. 第一阶段只上线 20—30 个高频组件和 12—18 个高频整页配方，覆盖大多数可研、经营汇报和项目决策场景。
4. 版式选择由内容语义、数据形态、字数容量和页面角色共同决定，不再只根据固定 `layoutId` 套一个页面。
5. 引入 CyberPPT 的证据链、逐页 manifest、双重质量门禁和返工清单，但不把“每页都先生成图片蓝图再逐页 1:1 还原”设为普通用户的默认流程。
6. 提供两种生成模式：日常快速模式和高标准汇报模式。前者重效率，后者才启用逐页蓝图、视觉对照和严格签发门禁。

## 二、当前小问题已修复

问题：上传 PPT 材料或点击 AI 生成后，“① 导入材料与建立证据包”会因为工作台重绘自动收起。

处理方式：工作台现在记录该区域最后一次展开状态。上传、AI 生成、规则生成、自动优化和视觉返修导致界面重绘时，保持用户原来的展开/收起选择。

验证结果：

- `ppt-qc.test.js`、`ppt-ai.test.js`、`ppt-core.test.js` 定向测试 13/13 通过。
- 浏览器实测：自动优化前 `open=true`，重绘后仍为 `open=true`。
- 本次仅修改 PPT 专属界面逻辑和脚本版本号，没有提交 Git。

## 三、对三类参考资料的判断

### 3.1 旧方法论文件

`0817AI_PPT输出能力增强_分步骤方法论.txt` 的阶段划分是有价值的，尤其是：

- 先保护基线，再做视觉增强；
- 新增商务蓝咨询风，而不是直接覆盖全部旧模板；
- 组件注册表与内容驱动选型；
- 预览与导出保持一致；
- 每批次有对应测试。

但旧方案中“160 页全部组件已经提取”的表述并不准确。实际参考输出只人工挑选了约 11 个页面/组件，不能代表完整模板。

### 3.2 `addition` 参考代码

可以借鉴：

- `ppt-lib.js` 的组件注册表思想；
- `pick(layoutId, data)` 的内容驱动选择入口；
- `design token` 统一配色、字体和间距；
- PPT 专属文件边界和测试文件组织；
- 组件保留来源页码，便于追溯模板出处。

不能直接复用：

- 组件提取器主要用正则解析 OOXML，容易漏掉组合、继承样式、主题色、关系文件和复杂图表；
- 部分中文文件已经出现乱码或字符串损坏；
- 组件库只有少量人工指定页，缺少全量聚类；
- 一些“组件”其实是整页元素复制，并没有形成可变文字槽位、容量约束和语义契约；
- 旧增强曾修改共享文件并破坏其他功能，不具备整体恢复条件。

因此，`addition` 只作为设计实验记录，不作为代码恢复源。

### 3.3 CyberPPT

CyberPPT 是 MIT 许可的开源 Codex Skill。其核心不是套模板，而是：材料证据表 → 2—3 条故事线比较 → SCR 收敛 → 逐页蓝图 → 可编辑还原 → 多重 QA 门禁。官方仓库还提供 PPTX 对象检查、渲染导出、渲染差异比较、组件签名和严格校验脚本。

最值得吸收的五点：

1. 每个数字、结论和建议都能回到证据来源。
2. 每页必须有“这一页想证明什么”和“SO WHAT”。
3. 生成前锁定逐页内容与组件清单，减少生成时跑偏。
4. 结构可编辑和视觉质量是两个独立硬门槛。
5. 失败后输出具体返工清单，而不是只显示一个总分。

不宜直接照搬的部分：

- 普通 PPT 每页都调用图片生成做蓝图，时间和算力成本过高；
- 逐页制作、逐页确认适合重要汇报，不适合日常快速材料；
- 像素级 1:1 对照会显著增加本地部署依赖和处理时间。

参考来源：

- [CyberPPT 官方仓库](https://github.com/crazyykhllc-bit/CyberPPT)
- [CyberPPT 质量保证规范](https://github.com/crazyykhllc-bit/CyberPPT/blob/main/references/quality-assurance.md)
- [CyberPPT PPTX 严格校验脚本](https://github.com/crazyykhllc-bit/CyberPPT/blob/main/scripts/validate_pptx.py)

## 四、160页模板实际结构

对用户提供的《160页高级商务蓝配色》PPTX 做只读 OOXML 盘点，结果为：

| 项目 | 数量 | 说明 |
|---|---:|---|
| 幻灯片 | 160 | 确实是完整 160 页 |
| Slide Layout | 17 | 说明大量页面共享基础版式 |
| Slide Master | 1 | 品牌底层结构比较统一 |
| Theme | 2 | 存在主主题与补充主题 |
| 媒体资源 | 96 | 包含图片、图标或其他媒体 |
| 原生图表 | 103 | 图表是模板的重要组成部分 |
| 嵌入对象 | 104 | 主要与图表数据工作簿等对象有关 |
| 文件大小 | 约 5.93 MB | 适合本地离线解析 |

关键判断：160 页不等于 160 个独立组件。更合理的拆分大致会形成：

- 8—12 个设计令牌组；
- 25—40 个基础组件；
- 15—25 个组合组件；
- 25—45 个整页配方；
- 若干封面、章节页、结尾页变体。

最终准确数量要由自动聚类结果和人工复核共同确定，不能事先硬写为 160 个组件。

## 五、目标产品形态

### 5.1 两种生成模式

| 模式 | 适用场景 | 工作流 | 预计速度 |
|---|---|---|---|
| 日常快速模式 | 周报、一般汇报、内部讨论 | 材料解析 → 证据包 → AI 故事线 → 自动选组件 → 导出 → 自动 QA | 快 |
| 高标准汇报模式 | 经营班子、董事会、正式汇报 | 证据包 → 多故事线比较 → SCR → 全页蓝图/线框 → 人工确认 → 逐页生成 → 严格 QA → 签发 | 较慢 |

### 5.2 用户实际看到的流程

1. 上传 Word、PDF、Excel、图片或粘贴文字。
2. 系统展示材料清单、数字事实、表格和来源。
3. AI 给出汇报目标、核心结论、SCR 故事线和建议页数。
4. 用户选择“快速生成”或“高标准汇报”。
5. 系统生成逐页卡片，每页显示：结论、证据、组件、数据图表、来源和容量风险。
6. 用户可锁定某页、换组件、改文字、重新生成单页。
7. 预览和导出使用同一份 `SlideSpec`、同一组件注册表、同一设计令牌。
8. 导出前输出结构 QA、视觉 QA、可编辑性 QA 和返工清单。

## 六、推荐技术架构

### 6.1 四层组件体系

#### 第一层：设计令牌 `DesignToken`

只定义品牌语言，不承载业务内容：

- 主色、辅助色、背景色、风险色；
- 标题/正文/数字/来源字号阶梯；
- 8pt 或 10pt 间距网格；
- 卡片圆角、阴影、描边、透明度；
- 图表颜色序列和强调规则；
- 页眉、页脚、页码和来源区。

#### 第二层：基础组件 `PrimitiveComponent`

例如：

- 标题条、章节号、来源脚注；
- KPI 卡、标签、结论条；
- 原生柱状图、折线图、饼图、瀑布图；
- 时间轴节点、流程节点、风险项；
- 图片框、图例、注释、箭头；
- 数据表、对比条、进度条。

#### 第三层：组合组件 `CompositeComponent`

例如：

- 左图右卡；
- 上结论下图表；
- 图表 + 3 个 KPI；
- 风险—影响—对策；
- 四阶段路径；
- 里程碑 + 甘特；
- 结论 + 证据 + 行动；
- 表格 + 关键发现。

#### 第四层：整页配方 `SlideRecipe`

定义页面角色、可用组件组合、槽位、容量和降级策略，不复制整页坐标代码。

```json
{
  "id": "chart_with_kpi_3",
  "role": "evidence",
  "sourceTemplatePages": [24, 57],
  "slots": {
    "title": {"maxChars": 28},
    "claim": {"maxChars": 46},
    "series": {"min": 2, "max": 8},
    "metrics": {"min": 2, "max": 3},
    "sources": {"required": true}
  },
  "fallback": "chart_with_commentary"
}
```

### 6.2 统一的逐页数据合同

所有预览与导出都读取同一份 `SlideSpec`：

```json
{
  "pageId": "p06",
  "role": "evidence",
  "title": "投资强度主要集中在建设中期",
  "soWhat": "资金安排应提前覆盖峰值季度",
  "evidenceIds": ["F-018", "T-003"],
  "componentIntent": "timeline_with_investment",
  "componentId": "gantt_kpi_combo_v1",
  "content": {},
  "sourceRefs": [],
  "locked": false,
  "qa": {}
}
```

这样可以解决当前最重要的长期问题：网页预览一种逻辑、PPT 导出另一种逻辑，最后成品与屏幕不一致。

### 6.3 组件选择评分

组件选择不要只写一连串 `if/else`，建议用可解释评分：

```text
总分 = 页面角色匹配 30%
     + 数据形态匹配 25%
     + 内容容量适配 20%
     + 叙事位置匹配 10%
     + 品牌风格匹配 10%
     + 历史人工选择偏好 5%
     - 溢出风险惩罚
     - 连续重复版式惩罚
```

每次选型记录前三名及原因，后台可看到“为什么选择这个版式”，便于后续持续训练规则。

## 七、160页模板吸收方式

### 7.1 全量扫描，但不全量硬编码

第一次离线扫描全部 160 页：

- 读取母版、布局、主题、关系文件；
- 识别文本、图片、形状、组合、图表、表格和嵌入对象；
- 提取坐标、层级、颜色、字体、字号、透明度、线宽；
- 形成每页结构指纹；
- 按几何结构、组件数量、主视觉和数据形态聚类；
- 输出缩略图联系表和聚类代表页；
- 人工确认哪些是“好组件”、哪些只是装饰或重复变体。

### 7.2 分三批注册

#### A批：最高价值组件

优先覆盖可研与经营汇报：封面、目录、章节页、KPI、柱线图、表格、流程、时间轴、风险对策、结论行动、图表 + 卡片、甘特 + 投资计划。

#### B批：复杂咨询组件

四象限、矩阵、价值链、因果树、路线图、阶段门、对比矩阵、组合图表、瀑布图、桑基/流向等。

#### C批：装饰和特殊页面

大图页、人物页、品牌故事页、特殊结尾、异形曲线、复杂装饰。只在高标准汇报模式中启用。

### 7.3 每个组件必须具备

- 唯一 ID 和版本号；
- 中文名称和适用场景；
- 来源模板页码；
- 可编辑槽位；
- 最少/最多数据项；
- 字数和字号下限；
- 预览渲染器与 PPTX 渲染器；
- 降级/拆页规则；
- 单组件样张；
- 自动测试和人工验收状态。

## 八、CyberPPT 的适配方式

### 8.1 直接纳入普通模式

- Evidence Gate：数字、判断、建议必须有来源或明确标记“待核实”。
- Storyline Gate：至少生成两个故事线候选，系统给出推荐理由。
- Density Gate：页面必须有结论、证据、图表/组件计划和 SO WHAT。
- Editable Layer Gate：标题、正文、数字、图表标签和来源保持可编辑。
- Container Overflow Gate：文字不能越过所属卡片、表格或结论条。
- Render QA Gate：导出成功不等于完成，必须有渲染结果检查。

### 8.2 只在高标准模式启用

- 全页视觉蓝图；
- 组件签名锁定；
- PPT 渲染图与蓝图 side-by-side；
- bbox/锚点差异；
- 像素差异图；
- 复杂曲线精确追踪；
- 逐页签发与通过页合并。

### 8.3 不建议采用

- 把整页蓝图图片直接当 PPT 背景；
- 为追求 100% 像素一致牺牲可编辑性；
- AI 自己声明“视觉完全通过”但没有渲染证据；
- 所有普通 PPT 都走昂贵的逐页图片生成流程。

## 十、测试策略：不应每次都跑“160页 + 全部165项”

这里要区分两种“160”：

- 160 页模板页面；
- 项目当前约 165 项自动化测试。

每次小改都全量跑两套，浪费时间，也不会提高对应缺陷的发现率。正确做法是分级测试。

| 改动级别 | 例子 | 必跑测试 | 是否扫描160页 |
|---|---|---|---|
| L1 小改 | 文案、按钮、单组件颜色、材料包展开状态 | 语法检查 + 相关 5—15 项定向测试 + 1—3 页样张 | 否 |
| L2 组件改动 | KPI卡、流程图、某个布局配方 | 组件测试 + PPT 导出测试 + 3—8 个代表页视觉检查 | 否 |
| L3 渲染器/选版器改动 | 设计令牌、坐标系统、内容选版规则 | 全部 PPT 测试 + 12—24 个聚类代表页 | 通常不全扫，只扫代表页 |
| L4 模板提取器改动 | OOXML 解析、聚类、主题继承 | 全 160 页结构扫描 + 全聚类检查 + 异常页报告 | 是 |
| L5 里程碑发布 | 一批组件正式上线、默认模板切换 | 全项目自动化测试 + 全 PPT 结构检查 + 代表页人工视觉审查 | 结构全扫；人工只审代表页与异常页 |

因此：

- 当前“材料包自动收缩”只需要定向测试和浏览器重绘实测，不需要跑 160 页模板。
- 改一个销售阶段或一个 PPT 组件，也不应该机械跑全部测试。
- 修改模板提取算法或进行正式版本发布时，才值得全量扫描 160 页。
- 全 160 页可以做自动结构检测；人工肉眼不必每次看 160 页，只看各聚类代表页和自动标红页。

## 十一、建议的验收指标

### 内容质量

- 100% 数字有来源或“待核实”标识；
- 90% 以上正文页有明确 SO WHAT；
- 同一页只表达一个主要判断；
- 无证据内容不会伪装成正式结论。

### 视觉质量

- 无文本越界、卡片溢出和明显重叠；
- 最小正文不低于约 11—12pt（特殊脚注除外）；
- 连续三页不使用完全相同主体布局；
- 网页预览与 PPTX 组件类型、数量和主要位置一致；
- 高标准模式下有渲染图、差异记录和返工结果。

### 可编辑性

- 标题、正文、关键数字、表格和常规图表保持原生可编辑；
- 复杂视觉资产允许图片化，但必须登记来源和不可编辑范围；
- 不使用整页截图冒充可编辑 PPT。

### 稳定性

- PPT 改动不影响测算、可研、知识库和数据分析；
- 定向测试与批次级全量测试分开；
- 每次批次上线前能恢复到上一个稳定版本。

## 十二、推荐执行顺序

下一步不直接做所有 160 页组件。建议按下列顺序推进：

1. 完成全量模板盘点器和聚类联系表。
2. 由聚类结果确定 A 批 20—30 个高价值组件。
3. 建立设计令牌、正式组件注册表和整页配方。
4. 先让 8—12 页真实项目材料在 A 批组件上跑通。
5. 完成预览/导出一致性和定向 QA。
6. 再上线高标准汇报模式和逐页蓝图。
7. 最后扩充 B/C 批组件，不断吸收真实使用反馈。

这条路线比“立即把 160 页全写进代码”更稳，也更容易得到真正好看的结果：系统学到的是模板的设计语言和组合能力，而不是只能复印旧模板。
