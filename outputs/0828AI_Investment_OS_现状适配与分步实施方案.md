# AI Investment OS 现状适配与分步实施方案

日期：2026-08-28
参考资料：`0828AI_Investment_OS_总体设计与分步开发路线图.md`
适用项目：`ai-studyreport-local`
文档性质：实施决策稿；本文件不代表已经完成对应代码。

## 一、结论先行

原方案的产品方向正确，约 **80%—85% 的思想可采纳**，但不能按照原文 Phase 0—11 从头建设。当前项目已经具备白箱测算、项目级对话恢复、参数影响预演、选择性更新、RAG/Wiki、联网证据、Claim—Evidence、报告版本、黄金项目评测、PPT生成、规则审核等能力。若重新建设 Document Studio、Presentation Engine、依赖图和证据底座，会造成重复系统和数据分裂。

更适合本项目的路线是：

> **保留现有专业引擎 → 建立统一项目大脑与适配层 → 补齐决策/任务/风险闭环 → 建项目驾驶舱 → 再做项目组合和组织智能。**

产品定位可以升级为：

> 面向保障房与投资项目的全周期智能工作平台，以项目为最高业务对象，把资料、事实、参数、测算、证据、结论、决策、任务、风险、报告、PPT和版本统一到一个可追溯、可恢复、可审签的项目工作空间中。

这不是把现有“AI可研”推倒重来，而是让它成为 Investment OS 中最成熟的“可研与投资决策”专业子系统。

## 二、原方案中应当直接保留的内容

| 原方案能力 | 采纳判断 | 与现有项目的关系 | 实施方式 |
|---|---|---|---|
| Project 作为最高业务对象 | 直接采纳 | 已有项目库、项目会话和项目恢复 | 用统一 `projectId` 串起各模块，不新建第二套项目库 |
| Project Brain | 直接采纳并列最高优先级 | 当前项目数据仍分散在会话、测算、报告、PPT、材料等结构中 | 建统一读模型和适配层，先聚合、后逐步规范化 |
| FACT / ASSUMPTION / CALCULATION / AI_JUDGEMENT | 直接采纳 | 已有白箱计算、参数来源、人工确认和证据链 | 升级为全项目通用信息类型，并要求输出携带类型与来源 |
| Evidence Graph | 继续深化 | 已有 Claim—Evidence—Source 与提交前审计 | 扩展到决策、会议、任务、风险和PPT，不另造图谱 |
| Metric Lineage | 改造后采纳 | 已有参数→指标→章节依赖图 | 增加指标→表格→报告结论→决策的下游关系 |
| Dependency Graph | 继续深化 | 已实现参数变化影响预演与选择性更新 | 扩展到项目阶段、任务、风险、材料和交付件 |
| Version / Diff / Undo | 继续深化 | 已有测算快照、报告版本、接受/拒绝/撤销 | 形成统一 ChangeSet，跨测算、报告、PPT联动 |
| Decision Ledger | 高价值新增 | 当前已有判断与审查，但未形成独立决策台账 | 优先补齐“议题—选项—依据—决定—责任人—影响” |
| Meeting → Decision → Task | 高价值新增 | 当前对话和项目流程已有基础 | 先做轻量闭环，不复制完整会议软件 |
| Project Cockpit | 高价值新增 | 当前项目管理仍以项目列表和功能入口为主 | 聚合项目阶段、待办、风险、测算、资料、报告和证据状态 |
| Scenario Lab | 改造后采纳 | 已有单参数曲线、低敏感扰动、影响预演 | 升级为可保存、可比较、可提交决策的情景方案 |
| Pre-Submission Audit | 继续深化 | 已有可研审核、测算标准、证据审计 | 扩展为投资决策包完整性和一致性审计 |
| Golden Project Validation | 直接采纳 | 已具备黄金项目数据模型、评测和后台治理 | 下一步重点是装入真实样本，而非继续搭框架 |
| Portfolio Brain | 延后采纳 | 单项目指标尚需统一，真实项目样本不足 | 至少3—5个真实项目稳定运行后启动 |
| Organization Intelligence | 长期保留 | 当前不具备足够组织级数据 | 真实运行6—12个月后再实施 |

## 三、需要改写或暂缓的内容

### 3.1 不重新建设已有模块

- “AI Document Studio”不再新建独立编辑器，现有可研逐章生成、材料缺口、选择性更新、AI修改、复核签发即为基础平台。
- “Presentation Engine V2”不再作为 Investment OS 的前置工程；现有AI PPT通过项目大脑读取事实、指标、证据和版本即可。
- Evidence、Dependency、Version 不再另建平行结构，统一扩展现有 `ReportEvidenceGraph`、`ReportDependency` 和 `ProjectWorkflow`。
- 项目管理不做 Jira 复刻，只做投资业务需要的阶段、决策、任务、风险、材料、交付件和审批。

### 3.2 不把数量当成果

以下指标不应成为当前目标：100个工具、2万条证据、1万条事实、百万级数据、多Agent数量。当前优先级应是：

1. 第二个真实项目能否少做重复工作；
2. 一个数字能否追到参数、公式、来源和版本；
3. 一个决策能否追到会议、证据、测算情景和责任人；
4. 项目变化后能否准确提示影响并只更新必要内容；
5. 真实用户能否在中断、刷新、切换设备后继续工作。

### 3.3 延后组织级建设

Portfolio Brain、资源统筹、跨项目知识推荐、组织级决策模式识别必须建立在统一指标口径和真实项目数据上。当前直接做会得到“漂亮但不可信”的组合看板。

## 四、现有能力与目标差距

| 目标层 | 当前可复用能力 | 主要缺口 | 优先级 |
|---|---|---|---:|
| 项目身份与恢复 | 项目库、复制、归档、恢复、项目会话 | 各专业模块未全部使用同一项目上下文 | P0 |
| 项目事实 | 项目信息、材料、参数、分析数据、联网证据 | 缺统一 Fact ID、类型、效力期、确认状态 | P0 |
| 参数与指标 | 白箱引擎、来源层级、人工确认、敏感性 | 缺跨引擎统一指标目录及指标版本 | P0 |
| 证据与结论 | RAG/Wiki、联网搜索、Claim—Evidence审计 | 决策、任务、PPT尚未全部绑定证据 | P1 |
| 版本与影响 | 测算快照、报告版本、参数影响、选择更新 | 缺跨模块统一变更集和项目时间线 | P1 |
| 决策管理 | 项目诊断、审查问题、人工签发 | 缺正式 Decision Ledger | P1 |
| 任务与风险 | Agent任务、材料缺口、审查问题 | 缺面向项目人员的责任人、期限、状态和升级 | P2 |
| 阶段管理 | 可研流程与项目进度 | 缺发现、初判、立项、决策、实施、投后、退出的统一阶段模型 | P2 |
| 项目驾驶舱 | 项目管理页、进度、资料/报告/测算状态 | 信息仍按功能分散，缺单页行动入口 | P2 |
| 情景决策 | IRR滑块、单参数曲线、联合扰动、影响预演 | 缺情景保存、比较、审批和决策引用 | P3 |
| 项目组合 | 无稳定的跨项目标准指标 | 需统一指标后再聚合 | P4 |
| 组织智能 | Wiki与规则沉淀 | 缺长期运行数据和组织反馈闭环 | P5 |

## 五、目标架构：一套项目大脑，多套专业引擎

```text
用户 / 管理员
      │
项目驾驶舱（阶段、决策、任务、风险、材料、成果、版本）
      │
Project Brain 统一项目上下文
 ├─ Facts        事实、假设、计算结果、AI判断
 ├─ Parameters   参数、来源、人工确认、版本
 ├─ Metrics      指标、单位、口径、计算血缘
 ├─ Evidence     文件、网页、知识库、Sheet/单元格、测算快照
 ├─ Decisions    议题、选项、结论、依据、影响
 ├─ Tasks/Risks  责任人、期限、状态、升级、处置
 ├─ Artifacts    可研、测算表、PPT、审查结果、会议纪要
 └─ Events       阶段、修改、审批、发布、回滚时间线
      │
专业能力适配层
 ├─ AI可研与审查
 ├─ 白箱财务测算
 ├─ 项目数据分析
 ├─ RAG / Wiki / 联网搜索
 ├─ AI PPT与素材中心
 └─ AgentCore工具与工作流
```

核心原则：专业模块继续负责专业计算和生成，Project Brain 负责统一身份、关系、版本、审计和调度，不在 Project Brain 内复制测算公式或报告生成逻辑。

## 六、建议的数据模型

### 6.1 复用而不是替换

现有 `projects`、项目工作流状态、测算快照、报告版本、分析快照、联网证据、Wiki/RAG、PPT项目继续保留。新增表首先作为统一索引和关联层，不进行一次性大迁移。

### 6.2 建议新增的最小表

| 表 | 关键字段 | 用途 |
|---|---|---|
| `project_facts` | id, project_id, fact_type, key, value_json, source_ref, confidence, status, valid_from/to, version | 统一事实/假设/计算/AI判断 |
| `project_metrics` | id, project_id, metric_key, value, unit, calc_snapshot_id, lineage_json, version | 统一指标目录与血缘 |
| `project_decisions` | id, project_id, stage, topic, options_json, decision, evidence_ids, scenario_ids, owner, status | 决策台账 |
| `project_tasks` | id, project_id, source_type/id, title, owner, due_at, priority, status | 决策、风险、材料缺口转任务 |
| `project_risks` | id, project_id, category, probability, impact, evidence_ids, response, owner, status | 风险台账 |
| `project_artifacts` | id, project_id, type, module_ref, version, status, evidence_audit_id | 报告、测算、PPT、纪要统一索引 |
| `project_events` | id, project_id, event_type, actor, payload_json, created_at | 项目时间线与审计 |
| `project_change_sets` | id, project_id, before_refs, after_refs, impact_json, approval_status | 跨模块变更、差异、接受/回滚 |
| `project_stage_history` | project_id, from_stage, to_stage, reason, approved_by, changed_at | 全周期阶段流转 |

所有迁移必须可重复执行、字段有默认值、旧项目可读取。第一阶段不删除旧字段，不要求旧项目一次性补齐。

## 七、重排后的七阶段实施路线

## 阶段0：冻结基线与建立项目上下文适配层（1—2周）

### 目标

不改变用户现有操作，把分散能力统一映射到 `ProjectContext`。

### 工作项

1. 盘点项目ID在可研、测算、数据分析、RAG、PPT、联网任务中的使用方式。
2. 定义 `ProjectContext V1`：项目身份、阶段、当前测算快照、当前报告版本、材料、证据、待办摘要。
3. 建只读聚合API，优先读取现有数据，不迁移正文和附件。
4. 为旧项目补兼容适配，不要求重新创建项目。
5. 建立接口契约测试和项目恢复测试。

### 验收

- 同一项目进入任一模块都能识别相同 `projectId`。
- 刷新、返回、跨模块后项目不丢失。
- 项目摘要中的测算、报告、证据、材料版本均可点回原模块。
- 现有项目无需重建即可使用。

## 阶段1：Project Brain V1 与四类信息治理（2—4周）

### 目标

形成统一事实、参数、指标、证据和成果索引。

### 工作项

1. 实现 `project_facts`、`project_metrics`、`project_artifacts`、`project_events`。
2. 把项目基本信息、人工确认参数、白箱测算结果、数据分析快照映射成统一事实。
3. 每项信息明确：类型、来源、确认人、效力期、版本和置信度。
4. 建立“冲突事实”提示，不自动覆盖人工确认值。
5. 在项目管理页增加“项目事实与成果”页签。

### 验收

- 任一关键数字能看到 FACT/ASSUMPTION/CALCULATION/AI_JUDGEMENT 标签。
- 人工确认事实优先级高于AI推断，冲突时提示而非静默覆盖。
- 旧测算、旧报告和PPT只做索引，不重复保存大文件。

## 阶段2：血缘、依赖、决策和统一变更集（2—4周）

### 目标

把现有参数影响图与证据图扩展成真正的决策链。

### 工作项

1. 扩展依赖关系：参数→指标→表格→章节→PPT页→决策。
2. 实现 `project_decisions`：问题、选项、依据、情景、决定、责任人、状态。
3. 实现 `project_change_sets`，记录参数修改前后、影响范围和选择性更新结果。
4. 将提交前证据审计应用到决策和PPT关键结论。
5. 建“为什么得到这个结论”侧栏。

### 验收

- 修改租金、建设期、成本等参数前可列出受影响指标、表格、章节和PPT页。
- 一个决策可反查采用的测算情景、政策、材料和会议记录。
- 接受修改后形成新版本；拒绝不污染当前正式版本；可撤销。

## 阶段3：全周期阶段工作台（3—5周）

### 目标

从“只在可研阶段使用”扩展为项目全生命周期入口。

### 阶段模板

1. 项目发现：机会来源、初始材料、相似项目。
2. 初步研判：政策适配、区位、需求、初步财务边界。
3. 立项：立项材料、审批要求、责任人和计划。
4. 可研与尽调：现有AI可研、数据分析、测算、审查能力。
5. 投资决策：方案比较、决策台账、签发包。
6. 实施：工期、投资计划、合同/变更、风险和里程碑。
7. 投后：经营指标、预算偏差、风险、定期复盘。
8. 退出/总结：退出条件、项目复盘和知识沉淀。

### 工作项

- 每阶段只配置进入条件、必备成果、审批点、任务模板和风险模板。
- 可研现有流程作为第4阶段直接嵌入，不复制页面。
- 阶段切换必须记录原因和审批，不允许静默跳转。

### 验收

- 用户能明确看到项目在哪个阶段、下一步做什么、缺什么、谁负责。
- 不同项目类型可以使用不同阶段模板，但共享同一项目大脑。

## 阶段4：Meeting → Decision → Task/Risk 与项目驾驶舱（3—5周）

### 目标

把讨论和结论变成可跟踪行动。

### 工作项

1. 支持上传会议纪要或粘贴会议内容，抽取议题、决定、待办和风险候选。
2. 人工确认后才进入正式决策、任务和风险台账。
3. 决策自动关联证据、情景、报告章节和PPT页。
4. 项目驾驶舱展示：阶段、关键指标、材料缺口、任务、风险、待审批、最新成果和变更。
5. 驾驶舱所有卡片必须能进入责任模块处理，不做只读装饰看板。

### 验收

- 会议内容可在3分钟内形成待确认的决定、任务和风险。
- 每项任务有责任人、期限、来源和状态。
- 驾驶舱能回答“项目现在怎样、为什么、下一步谁做什么”。

## 阶段5：Scenario Lab 与投资决策包（2—4周）

### 目标

把现有敏感性和预演能力升级为正式方案比较。

### 工作项

1. 支持保存基准、乐观、审慎和自定义情景。
2. 情景调用同一白箱引擎，不允许AI自行计算关键财务数字。
3. 比较IRR、NPV、回收期、总投资、资金缺口和关键风险。
4. 将选定情景绑定决策台账并形成投资决策包。
5. 提交前执行口径、证据、材料、测算勾稽、报告/PPT一致性审计。

### 验收

- 情景结果可重复计算并与测算表一致。
- 决策包中的每个关键数字均可追溯。
- 存在阻断级问题时不能误标为“已审查通过”。

## 阶段6：真实项目验证与生产化（贯穿前5阶段，集中2—4周）

### 目标

用真实项目决定功能是否有效，而不是继续堆概念。

### 工作项

1. 脱敏导入5—20个真实黄金项目，覆盖出租、出售、非居改保。
2. 建业务场景测试：材料缺失、参数改变、证据冲突、报告更新、决策签发、恢复与回滚。
3. 记录人工耗时、AI耗时、修改率、证据覆盖、数字错误、审查发现率。
4. 完成50人并发、长任务队列、失败恢复、备份和SLO告警。
5. 建 Optimization Ledger，记录每次优化、证据和实际收益。

### 验收

- 第二个同类项目人工投入显著下降。
- 关键数字错误为0，证据覆盖和缺口识别达到约定阈值。
- 50人使用时核心路径达到SLO，失败任务可恢复。

## 阶段7：Portfolio Brain 与组织智能（满足门槛后4—8周起）

### 启动门槛

- 至少3—5个真实项目持续运行；
- 核心指标口径统一；
- 项目事实、阶段、决策、任务和风险的数据完整度达到80%以上；
- 权限和部门隔离已完成。

### 首批功能

- 跨项目投资、进度、收益、资金缺口和风险对比；
- 项目优先级与资源冲突提示；
- 相似项目与历史决策推荐；
- 组织常见错误、规则改进候选和经验复用。

不得先做“AI自动决定投不投”；系统给出证据充分的建议和比较，由有权限人员决策。

## 八、首个30天建议开发包

### 第1周：统一项目身份

- 完成项目ID与模块数据源盘点。
- 定义 `ProjectContext V1` 和只读聚合API。
- 补项目刷新、切换和跨模块恢复测试。

### 第2周：项目大脑最小数据层

- 新增事实、指标、成果、事件四张表。
- 接入项目基本信息、当前测算快照、当前报告版本、证据摘要。
- 建兼容层，不迁移大附件。

### 第3周：决策台账

- 新增决策表和最小前端。

## 九、建议API边界

为避免继续扩大单文件，建议按职责拆分：

- `GET /api/projectbrain?projectId=`：聚合只读摘要。
- `POST /api/projectfacts`：事实候选、人工确认、冲突处理。
- `GET/POST/PATCH /api/projectdecisions`：决策台账。
- `GET/POST/PATCH /api/projecttasks`：任务台账。
- `GET/POST/PATCH /api/projectrisks`：风险台账。
- `GET /api/projecttimeline`：统一事件时间线。
- `POST /api/projectchanges/preview`：跨模块影响预演。
- `POST /api/projectchanges/apply`：审批后形成变更集。

API必须校验项目权限、用户身份、版本号和幂等键；外部工具失败不得破坏项目主记录。

## 十、测试与迁移策略

1. **双轨读取**：先从现有数据读取并映射，Project Brain 不成为新的数据孤岛。
2. **增量写入**：新创建或新确认的数据写统一模型；旧项目按访问逐步补索引。
3. **禁止大爆炸迁移**：不一次性重写项目JSON、报告正文和PPT数据。
4. **契约测试**：每个专业模块只承诺输出必要摘要、版本和引用ID。
5. **黄金项目测试**：每阶段至少用一个真实项目验证，不只用模拟数据。
6. **高风险全量回归**：数据库、公共项目结构、鉴权、计算或导出改变时执行全量测试。
7. **性能基线**：Project Brain摘要接口不加载大附件；默认只返回摘要，详情按需加载。

## 十三、实施中的三条红线

1. 不允许AI直接编造财务数字；所有关键数值必须来自白箱引擎、正式数据或明确人工输入。
2. 不允许Project Brain复制专业模块正文和大附件形成第二套事实；统一索引、ID、版本和关系即可。
3. 不允许为了“全周期”一次性铺开所有阶段；必须以真实项目逐阶段验收，任何阶段没有用户价值证据就暂停扩张。

## 十四、建议的下一步

如确认本方案，先实施“阶段0 + 阶段1的最小闭环”：

1. 建立统一 `ProjectContext V1`；
2. 新增项目事实、指标、成果、事件的最小数据层；
3. 让现有可研、测算、证据、PPT继续工作，只增加统一索引；
4. 用一个真实项目验证跨模块恢复与溯源；
5. 验证通过后再开始 Decision Ledger，不直接做Portfolio Brain。

这一步完成后的直接变化是：用户不再面对多个互相独立的AI工具，而是进入一个项目后，所有资料、测算、可研、证据、PPT、决策和版本都围绕同一项目持续工作。
