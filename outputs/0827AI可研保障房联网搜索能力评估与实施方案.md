# AI可研保障房联网搜索能力评估与实施方案

> 日期：2026-08-27  
> 评估对象：当前 `ai-studyreport-local` 本地版本  
> 参考资料：《保障房项目信息搜索工作流 v3.0（含GitHub开源替代）》  
> 本文只确定方案，不在本阶段接入外部搜索服务。

## 一、先给结论

当前系统已经有“局部联网能力”，但还没有“通用网上搜索闭环”。

- 已有：高德地理编码、位置候选人工确认、1/3/5km POI与周边设施、竞品公寓、职住平衡代理指标。
- 已有：内部RAG知识库、知识Wiki、正式资料台账、Excel单元格溯源、项目数据分析、白箱测算引擎。
- 已有：可研逐小节逻辑库能标出“需知识库检索、需网上检索、需数据接口、需测算、需人工上传”。
- 缺少：真正的通用网页搜索工具、网页/PDF全文读取、来源可信度分级、跨来源核验、网页证据台账、检索结果自动写入小节。
- 因此，目前“需网上检索”表示**这项材料应该从网上找**，不表示系统已经去找，更不表示已经找到。

建议不要一次性安装很多MCP。最优路径是先在现有AgentCore里建立统一的 `WebResearchTool` 工具网关，先接一个稳定搜索Provider和一个网页正文提取器；等这条主链路稳定，再把MCP作为可插拔Provider接入。

### 现状的准确定位

当前属于：

> “内部资料RAG + 地图/POI垂直接口 + 材料缺口识别”

目标应升级为：

> “内部资料优先 + 权威网络检索 + 网页全文取证 + 多源核验 + 证据入账 + 逐节引用”

## 三、豆包工作流中值得直接吸收的内容

### 1. 四维检索框架

直接采用“规划—政策—市场—项目”四类信息框架。这与当前可研章节天然对应：

- 规划：国土空间规划、住房发展规划、年度建设筹集计划、片区规划。
- 政策：保障房类型、准入、租售价格、补贴、建设运营、配售管理。
- 市场：人口、住房供需、租金/售价、库存、成交、产业与就业。
- 项目：宗地公告、招拍挂、立项、环评、施工许可、招标、同类案例。

### 2. 先识别住房类型再搜索

直接采用。搜索前必须明确出租、出售、非居改保、公租房、保租房、配售型保障房等业务口径。相同关键词在不同类型下含义不同，不能混搜后直接写入报告。

### 3. 国家—省—市—区分层搜索

直接采用。它能解决政策效力层级和地方细则遗漏问题。每条政策证据都必须记录：发布机关、文号、效力状态、发布日期、施行日期、适用区域、适用类型。

### 4. 权威来源白名单

直接采用并进一步固化为后台可维护表。默认可信级别：

1. 政府官网、政府公报、法规库、规划和自然资源部门。
2. 住建、统计、发改、财政、住房保障等公共机构。
3. 国企/上市公司公告、REIT披露、正式招投标与交易平台。
4. 有授权的专业数据服务商。
5. 主流媒体。
6. 自媒体、聚合站和营销页面只作为线索，不能单独支撑结论。

### 5. 搜索—精读—去重—交叉验证

直接采用。搜索摘要不能直接成为报告依据；至少打开关键原文，提取正文、表格或附件，并保存原始URL和抓取时点。

### 6. 结构化输出和交付前自检

直接采用。每个结论要能回答：

- 搜到了什么？
- 来源是谁？
- 什么时候发布、什么时候抓取？
- 对哪个地区、哪类保障房有效？
- 是否与其他来源冲突？
- 最终写进了哪个章节？

## 四、需要改造后再采用的内容

### 1. 各类“搜索工具名”不能直接照搬

原方案里的 `general_search`、`seed_legal_search`、`seed_finance_search`、`enterprise_agentic_search` 更像能力名称，不一定是可直接调用的公开接口。当前项目应把它们统一映射成自己的工具契约，而不是让业务代码绑定某个平台名称。

建议统一为：

- `search_web`：通用搜索，支持域名、时间、地区过滤。
- `fetch_web_source`：读取网页、PDF、Word或公开附件全文。
- `search_policy`：基于权威域名白名单和政策字段的垂直搜索。
- `verify_web_claim`：对一个数字或结论做多源核验。
- `save_web_evidence`：保存证据并关联报告章节。

### 2. 开源MCP适合作为Provider，不适合作为业务核心

[web-researcher-mcp](https://github.com/zoharbabin/web-researcher-mcp) 已提供搜索、全文读取、可信站点Lens、引用验证和研究会话等能力，值得借鉴其“来源Lens、全文读取、引用验证、会话恢复”设计；但当前项目不宜把整个报告流程直接交给它控制，应通过统一适配层调用。

[Open-WebSearch MCP](https://github.com/LADLABS/MCP_open-webSearch) 可以作为低成本试验Provider，但公共搜索引擎抓取容易受页面变化、验证码、频率限制和服务条款影响，不宜作为企业生产环境唯一来源。

[Microsoft Playwright MCP](https://github.com/microsoft/playwright-mcp) 适合动态网页、必须执行JavaScript的页面和少量人工登录场景。它资源消耗较大，不应作为普通网页的默认抓取器，只做失败兜底。

### 3. 法律和金融开源项目要谨慎

- 许多法律MCP面向美国或欧洲案例库，不适合直接替代中国大陆法规和深圳政策检索。
- AKShare、yfinance等金融工具不能替代保障房政策、深圳住房市场和项目公告数据。
- 中指、Wind等授权数据未来应走独立Provider，不能与公开网页抓取混成同一种来源。

## 五、本阶段不建议采用的内容

- 不一次接入十几个MCP服务，避免依赖膨胀、错误边界不清和运维困难。
- 不自建全网爬虫或Elasticsearch互联网索引，当前投入产出比过低。
- 不让AI只看搜索摘要就生成政策结论或关键数字。
- 不把“搜索到1条页面”自动标记为“材料已齐”。
- 不承诺免费搜索Provider永久可用或固定额度；这些外部条件会变化。
- 不对每个小节都跑耗时的深度研究。普通章节用快速检索，决策关键数字才升级多源核验。
- 不先做图片搜索。当前最重要的是政策、数字、表格和来源证据。

## 六、推荐总体架构

```text
AI可研 / AgentCore
        │
        ├─ 先查：项目正式资料、Excel、白箱测算、RAG、Wiki
        │
        └─ WebResearchTool 统一网关
              ├─ QueryPlanner（住房类型、行政层级、章节、统计期）
              ├─ SearchProvider适配器
              │     ├─ 主搜索服务
              │     ├─ 备用搜索服务
              │     └─ MCP Provider（后续可插拔）
              ├─ FetchExtractor
              │     ├─ 普通HTML/PDF/附件读取
              │     └─ Playwright动态页面兜底
              ├─ EvidenceNormalizer（字段标准化）
              ├─ DedupAndVerify（去重、交叉核验、冲突检测）
              ├─ SourceLedger（来源台账、时间、哈希、版本）
              └─ ReportBinder（绑定逻辑项、小节和待补占位符）
```

核心原则：MCP只是工具接入方式，不是业务数据模型。无论未来接中指、Wind、Brave、Tavily、公开搜索或内部MCP，最终都必须转成相同的证据记录。

## 八、分步实施计划

### 第1批：建立真正可用的通用搜索底座

目标：让AgentCore能真实执行一次网页搜索，并返回可点击来源。

拟新增：

- `functions/api/websearch.js`：统一搜索API。
- `functions/api/_web-providers.js`：Provider适配器、超时、熔断、主备切换。
- `web-research-tools.js`：向AgentCore注册 `search_web`。
- 环境变量：`WEB_SEARCH_PROVIDER`、对应API URL/Key、超时和最大结果数。

验收：

- 能按关键词、域名、地区和日期返回真实结果。
- 单个Provider失败不会拖垮AI可研其他功能。
- 不向前端暴露Key，不显示原始 `fetch failed`。
- 返回结果必须含标题、URL、摘要、来源、检索时间。

### 第2批：网页全文和附件取证

目标：不只读搜索摘要，能打开政府网页、PDF和公开附件。

拟新增：

- `functions/api/webfetch.js`。
- 静态HTML正文提取、PDF文字和表格提取、附件类型识别。
- 动态页面失败后才调用Playwright类兜底。
- URL安全检查、下载大小限制、超时和内容类型白名单。

验收：

- 至少覆盖普通网页、PDF、Word附件三类来源。
- 保存原始URL、正文哈希、发布时间和抓取时间。
- 页面发生变化时能识别为新版本，而不是覆盖旧证据。

### 第3批：保障房垂直搜索计划器

目标：把豆包方案的搜索方法变成可执行规则。

能力：

- 自动识别出租、出售、非居改保等项目类型。
- 按国家、省、市、区、项目五层生成查询。
- 按规划、政策、市场、项目四维生成任务。
- 可研小节只发与该节相关的查询，避免全报告重复搜。
- 最多3个搜索任务并行，控制等待时间和额度。

验收：

- 后台可查看本次搜索计划及每条查询对应的小节。
- 用户可删减、补充或重跑单条查询。
- 同一URL和同一文件自动去重。

### 第4批：来源治理与交叉验证

目标：让“搜到”升级为“可用于可研”。

规则：

- 关键政策优先官方原文；转载仅作线索。
- 关键数字至少两条独立来源，或一条权威原始统计来源。
- 同一机构转载不算两条独立来源。
- 自动检查统计期、行政区域、住房类型和单位是否一致。
- 冲突结果不自动选边，展示差异并要求人工确认。

验收：

- 每条证据都有可信等级和验证状态。
- 过期、失效、区域不符、类型不符的材料不会自动进入正文。
- 可从结论反查原文，也可从原文反查使用章节。

### 第5批：接入材料台账和逐节生成

目标：把现有“需网上检索”真正闭环。

前台变化：

- 红色“需网上检索”旁增加“开始检索”。
- 检索中展示查询、来源和处理进度。
- 找到但未核验显示黄色；核验通过显示绿色。
- 用户可选择哪些证据用于当前小节。
- 生成正文时在段落和数字旁显示来源，Word导出保留来源清单。
- 数据变化后标记受影响章节，只更新未锁定章节。

验收：

- 没找到资料时仍生成通用分析框架，但关键事实保持红色待补，绝不编造。
- 上传正式资料后，正式资料优先级高于网络证据。
- 网络证据更新不会静默覆盖人工确认内容。

### 第6批：MCP与专业数据服务扩展

目标：主链路稳定后再扩展。

- 将 `web-researcher-mcp` 或其他MCP接为Provider之一。
- 中指、Wind、内部数据平台各自实现独立Provider。
- 动态登录站点在授权、合规和账号许可明确后接入。
- 增加Provider健康看板、失败率、延迟、调用量和额度告警。

## 九、建议的文件边界

| 文件 | 职责 |
|---|---|
| `functions/api/websearch.js` | 搜索API入口、鉴权、限流 |
| `functions/api/webfetch.js` | 网页/PDF/附件全文读取 |
| `functions/api/_web-providers.js` | 搜索Provider适配、主备和熔断 |
| `functions/api/_web-evidence.js` | 证据标准化、去重、可信度和冲突 |

| `web-research-tools.js` | AgentCore工具注册，不放页面业务逻辑 |
| `aireport.js` | 材料缺口、检索进度、人工选择和逐节绑定 |
| `report.js` | 生成时只消费已确认或允许使用的证据 |
| `admin.html` | 权威域名、Provider、查询模板和来源治理 |

## 十、安全与合规边界

- 密钥只能在服务端环境变量中，不进入浏览器、日志、报告和Git。
- 内部项目资料不得自动发送给公网搜索服务；搜索查询只携带必要的公开关键词。
- 防止SSRF：禁止访问本机、内网IP、云元数据地址和非白名单协议。
- 抓取遵守网站条款、robots和访问频率，不绕过登录、验证码和付费墙。
- 任何外部网页内容都视为不可信数据，不能执行其中的指令。
- 保存证据摘要和必要原文，不无边界复制受版权保护内容。
- 用户可查看“这段内容用了哪些外部来源”，管理员可停用、归档或替换来源。

## 十一、速度和成本策略

- 第一层：项目正式资料、测算、RAG和Wiki，最快且最可信。
- 第二层：快速网页搜索，只取5—10条候选。
- 第三层：只对最相关的2—3条做全文抓取。
- 第四层：仅对关键政策、租售价、人口和供需数字做多源核验。
- 缓存相同查询和相同URL，按内容哈希判断是否需要重新抓取。
- 普通章节目标5—12秒返回候选；深度核验作为后台任务，不阻塞整份报告。

## 十二、最终成果形态

完成后，用户在AI可研中看到的不再只是“需网上检索”，而是：

1. 系统列出该小节为什么要搜索、准备搜什么。
2. 自动搜索官方政策、统计数据、项目公告和可信市场来源。
3. 展示候选来源、可信等级、统计期和适用范围。
4. 对关键数字做交叉核验，冲突时请用户确认。
5. 用户确认后，材料台账由红色转绿色。
6. AI按已确认来源完成小节正文、表格和待补提示。
7. Word报告保留来源清单，数字可追溯到URL、原文、统计期和版本。
8. 来源更新时只提示并预演受影响章节，不擅自改动正式报告。

## 十三、建议的推进决定

建议确认后从第1批开始，但第1批只接一个主Provider，不同时安装多个MCP。第1—2批打通后先用一个真实保障房项目测试，再决定是否进入第3—6批。

第一阶段的成功标准不是“能搜网页”，而是：

> 能把一条真实、可信、可复核的网页证据，安全地绑定到一个可研小节，并让报告引用它而不编造。
