# 企业级Agent框架评估与升级实施方案

> 2026-08-26实施状态：以“整体升级约50%”为本批目标，Run/Step/Checkpoint/Approval运行账本、工具风险元数据与熔断、四层上下文契约、Skill Candidate审核骨架和后台运行概览已经落地。后台Worker关页续跑、多Agent调度、Token成本账本、Skill自动评测发布和部门ABAC属于下一阶段，未提前宣称完成。学习与核心代码总览见《0826Agent学习总成.md》。

> 评估日期：2026年8月26日  
> 评估对象：AI可研报告生成、白箱测算、知识库、项目数据分析、AI PPT及本地服务整体架构  
> 参考资料：`code_20260826.txt`、当前项目代码、现有自动化测试、LangGraph/AWS官方框架文档及Nous Research `hermes-agent`源码与官方文档

## 一、结论先行

当前系统已经不是普通“聊天机器人”，而是一个**面向可研与投资决策的受控业务智能体系统**。它具备项目级状态、工具调用、确定性测算、RAG/Wiki、规则治理、人工确认、报告版本和业务审查闭环，适合进入企业内部真实项目试运行。

但如果把“企业级”定义为：可承载长期运行任务、服务重启后从精确步骤恢复、工具权限可统一治理、每一步可追踪评测、部门数据严格隔离、具有SLO和自动告警，那么当前仍处于**企业级应用的准生产阶段**，综合约70分，尚未达到成熟平台的85分以上水平。

最重要的判断：

1. **不建议整体重写为LangChain。** 现有白箱测算、逐章生成、项目工作流和管理后台已经形成大量稳定业务资产，整体替换会扩大风险，且不会自动解决权限、审计、评测和运维问题。
2. **建议保留自研AgentCore作为业务编排层。** 当前 `agent-core.js` 已具备工具注册、参数校验、有限轮ReAct、自查、长期记忆和链路日志，适合受控业务场景。
3. **只对“长任务、可中断、可恢复”的流程引入运行时增强。** 可以先自研轻量Checkpoint；当流程复杂度继续上升时，再把可研批量生成、资料补全、复核签发等长流程接入LangGraph.js，而不是替换整个系统。
4. **AWS Bedrock AgentCore与项目里的自研AgentCore不是同一产品。** AWS AgentCore是AWS托管运行平台，支持任意框架和模型，也支持VPC连接，但仍依赖AWS账户和托管基础设施；如果公司要求完全本地、离线和数据不出内网，则不宜作为主运行底座。

## 二、对TXT方案的取舍

| TXT观点 | 评估 | 本项目采用方式 |
|---|---|---|
| 纯手写Agent维护成本高 | 部分正确 | 不再无限扩写单文件ReAct循环，逐步拆分运行时、工具网关、策略、追踪和评测模块 |
| LangChain TS适合本地化 | 正确，但不是必须整体迁移 | 仅复用成熟组件；复杂长流程优先评估LangGraph.js的Checkpoint与HITL |
| AWS AgentCore不适合纯内网 | 基本正确 | 不作为当前主方案；公司未来允许AWS VPC托管时再评估 |
| 数值必须与AI解耦 | 完全正确 | 继续坚持白箱测算引擎为唯一财务数值来源 |
| 工具热更新应配置化 | 正确 | 把工具元数据、权限、版本、超时、重试、幂等和审计策略沉淀到数据库 |
| Agent必须有循环熔断 | 已部分实现 | 从“最大轮数”升级为总耗时、单工具次数、总成本和重复调用联合熔断 |
| 长对话需要压缩 | 当前不足 | 增加项目事实、用户偏好、任务状态、最近对话四层上下文模型 |
| 需要容器化和权限体系 | 正确 | 作为服务器部署前的强制准入项，不等待业务量变大后再补 |

## 三、当前框架已经具备的企业能力

### 1. 受控工具调用

- `agent-core.js` 提供统一工具注册表、白名单工具集合、参数校验、最大轮数和调用轨迹。
- 写入、发布、测算确认等高风险动作仍由业务页面设置人工闸门。
- 财务数字来自 `nrcalc.js`、`rentcalc.js`、`salecalc.js`、`investestimate.js` 等确定性引擎。

### 2. 项目级状态与版本

- `aireport_project_sessions` 按用户和项目保存会话状态。
- `project-workflow.js` 已支持参数影响、测算快照、报告版本、接受/拒绝、撤销、人工锁定和返回上一步。
- 报告版本与测算快照绑定，避免正文和数字脱节。

### 3. 知识与证据治理

- 本地PostgreSQL、pgvector、Ollama向量接口形成RAG底座。
- Wiki具备草稿、发布、归档、版本和发布后进入RAG的治理闭环。
- Excel数字可记录文件、Sheet、单元格、统计期和版本来源。

### 4. 多模型与本地部署

- 已支持DeepSeek、GLM、Qwen及云端兜底的Provider顺序与故障切换。
- Hono + Node + PostgreSQL适配Cloudflare API代码，本地与云端业务处理器共享。
- 密钥来自环境变量，Provider状态接口不暴露URL和Key。

### 5. 可观测与质量控制基础

- `agent_traces` 记录问题、轮次、工具调用、答案和耗时。
- 管理后台已有用量、向量缓存和Agent调用统计基础。
- 当前代码约232个源文件、801.23万字节、约67,505行；本次抽查的模型切换与项目工作流22项测试全部通过。

## 四、距离成熟企业级还差什么

### 1. Agent运行仍主要在浏览器

当前ReAct循环运行于前端页面。页面关闭、浏览器崩溃或服务重启后，不能从某一次工具调用边界精确恢复；这与“项目状态能恢复”不同。企业运行需要服务端Run、Step、Checkpoint和幂等键。

### 2. 人工确认是业务页面能力，不是统一策略能力

目前不同页面分别实现人工确认。未来工具越来越多后，需要统一策略：只读工具自动执行，外部查询按数据级别控制，写数据库、发布知识、修改公式和导出正式成果必须审批。

### 3. 参数校验还不是强结构化契约

现有轻量校验可处理必填和枚举，但缺少统一JSON Schema/Zod契约、响应结构校验、版本兼容和错误字段定位。

### 4. 追踪粒度不足

目前主要记录一次Agent调用的汇总信息，且工具与答案存在长度截断。成熟系统需要Run→Step→Model→Tool四级Trace，记录状态、耗时、重试、错误类别、输入输出摘要、证据ID和Token成本，同时对敏感信息脱敏。

### 5. 缺少稳定的Agent评测集

代码回归测试较丰富，但还缺少真实项目问答、工具选择、材料缺口、政策引用、数字一致性、拒答边界和长流程恢复的标准评测集，无法量化每次Prompt或模型切换是否变好。

### 6. 企业权限和隔离仍需细化

当前已有用户与管理员区分，但部门、项目密级、资料可见范围、工具权限、导出权限和审批角色尚未形成统一RBAC/ABAC策略。

### 7. 缺少通用异步任务和SLO

PPT生图已有局部并发队列，但可研批量生成、OCR、批量入库、批量审查还没有统一任务队列、优先级、取消、断点续跑和失败重放。系统也缺少明确的成功率、P95延迟、恢复时间和告警阈值。

## 五、分阶段实施路线

### 第一阶段：建立服务端Agent Run底座（最高优先级）

目标：页面关闭后任务仍可继续，失败后从最后成功步骤恢复。

1. 新增 `agent_runs`、`agent_steps`、`agent_checkpoints`、`agent_approvals` 四类数据结构。
2. 每次任务生成 `run_id`、`project_id`、`user_id` 和幂等键。
3. 把模型调用、工具调用、自查、人工确认拆成明确Step。
4. 每个Step保存输入摘要、输出摘要、证据ID、状态、耗时、重试次数和错误分类。
5. 前端仅订阅进度和提交人工决定，不再承担整个Agent循环。
6. 首先接入“逐章生成”和“材料补充后选择性更新”，验证后再接其他流程。

验收：关闭页面后重新进入可看到任务状态；服务重启后可从最后成功Step继续；重复点击不会重复写入或重复扣费。

### 第二阶段：统一工具网关与权限策略

目标：工具可发现、可配置、可授权、可审计。

1. 为每个工具增加版本、所有者、读写等级、数据密级、超时、重试、幂等、是否需人工审批等元数据。
2. 工具执行前统一进行Schema校验、权限判断、项目范围判断和审批判断。
3. 外部Provider设置独立超时、错误边界和熔断状态，单一Provider失败不能拖垮其他通道。
4. 核心公式工具、正式发布工具和删除工具禁止由AI动态修改。
5. 后台提供工具启停、版本发布和调用成功率面板，但修改先进入草稿，审核后生效。

验收：越权工具调用被拒绝并留下审计记录；工具更新可灰度发布和回滚；同一外部服务连续失败后自动熔断。

### 第三阶段：结构化输出与上下文治理

目标：减少幻觉、上下文污染和长对话退化。

1. 使用JSON Schema或Zod定义工具入参、工具返回、章节草稿、审查问题和参数建议。
2. 上下文拆为四层：项目确认事实、任务状态、用户长期偏好、最近对话。
3. 对长对话生成可审阅摘要，关键项目事实不可被摘要覆盖。
4. RAG只注入当前步骤必要证据，禁止把整库内容灌入Prompt。
5. 所有关键数字在输出后与测算快照做二次勾稽。

验收：结构化输出解析成功率≥99%；长对话30轮后项目关键事实不丢失；报告数字与测算快照一致率100%。

### 第四阶段：全链路可观测与Agent评测

目标：知道Agent为什么成功、为什么失败、哪次升级真正有效。

1. 采用OpenTelemetry语义建立Run、模型、工具、RAG和数据库Span。
2. 建立至少200条真实业务评测集，覆盖三类项目、正常流程、缺资料、错误参数、外部服务失败和越权请求。
3. 指标包括：工具选择准确率、参数抽取准确率、证据引用覆盖率、数字一致率、章节完整率、人工修改率、任务成功率和P95耗时。
4. 每次模型、Prompt、工具说明或RAG策略更新前后运行对比评测。
5. 管理后台展示失败聚类、低质量章节、人工修改热点和高成本任务。

验收：所有生产任务可按run_id完整追踪；核心评测指标有基线、有目标、有趋势；升级不能只凭主观感觉发布。

### 第五阶段：企业权限、队列与部署

目标：支持50人以上并发和正式内网运行。

1. 建立部门、项目、角色、密级和动作五维权限模型。
2. 引入统一异步任务队列；初期可使用PostgreSQL任务表，规模增大后再接Redis/BullMQ。
3. AI服务、计算引擎、文档解析和向量服务按职责拆分进程，设置资源上限。
4. Docker化部署，增加健康检查、滚动升级、数据库备份和恢复演练。
5. 定义SLO：任务成功率、P95响应、最长恢复时间、队列积压和外部Provider可用率。

验收：50个用户并发时核心测算不阻塞；任务失败可重试和重放；部门间资料不可越权访问；备份可真实恢复。

### 第六阶段：选择性引入LangGraph.js

只在以下场景引入：

- 跨小时运行的批量资料解析、逐章生成和全报告复核；
- 需要多次人工中断、审批后继续的流程；
- 需要从任意Checkpoint回放、分支对比和故障恢复的流程；
- 未来出现真正的多Agent分工，例如资料Agent、测算Agent、写作Agent、审查Agent。

不迁移的部分：白箱公式、现有业务规则库、表格模板、RAG/Wiki数据、前端交互、已有API及稳定的短流程工具。LangGraph.js只作为长任务运行时适配层。

## 六、技术选型建议

| 能力 | 当前建议 |
|---|---|
| 短问答与单次工具调用 | 继续使用自研AgentCore |
| 可研项目业务状态 | 继续使用现有项目工作流和PostgreSQL |
| 长任务Checkpoint | 先自研最小Run/Step；复杂后引入LangGraph.js |
| 工具契约 | JSON Schema/Zod |
| 队列 | PostgreSQL任务表起步，必要时BullMQ/Redis |
| 追踪 | OpenTelemetry + 本地PostgreSQL/可视化面板 |
| 评测 | 自建真实项目评测集，不依赖外部云平台 |
| 企业权限 | 本地RBAC+项目/部门/密级ABAC |
| AWS AgentCore | 当前不采用；仅在公司允许AWS托管和VPC模式时重新评估 |

## 七、优先级与预计效果

1. **P0：服务端Run/Step/Checkpoint、幂等、统一审批**——解决“任务不够企业级”的根问题。
2. **P0：结构化契约、工具权限和外部Provider熔断**——减少错误调用和连带故障。
3. **P1：评测集、全链路Trace和SLO**——让质量提升可量化。
4. **P1：部门/项目/密级权限和统一任务队列**——支撑正式内网多用户。
5. **P2：选择性接入LangGraph.js**——仅用于复杂长流程，不进行全系统重写。

完成前三阶段后，企业级能力预计可由约70分提升到80–84分；完成权限、队列、生产验证和SLO后，可达到85分以上的正式企业内部应用水平。

## 八、Hermes Agent对本项目的增量启示

### 1. 总体判断：吸收治理机制，不复刻通用电脑代理

Nous Research的Hermes Agent定位是可操作终端、文件、浏览器和多种消息渠道的通用个人代理；本项目则是可研、财务测算、审查和知识治理的企业垂直智能体。两者目标不同，因此不建议引入Hermes Python运行时，也不建议让AI获得通用终端权限。

Hermes真正值得吸收的是其经过长期运行验证的六类工程机制：**事实记忆与流程技能分离、技能渐进加载、技能写入审批、会话压缩与谱系、按场景启用工具集、OS级安全隔离**。这些机制可以直接补强本方案前三阶段，不需要重写现有业务模块。

### 2. 可直接吸收的能力

| Hermes机制 | 本项目现状 | 建议落地方式 | 优先级 |
|---|---|---|---|
| 事实记忆与流程技能分离 | 已有用户记忆、RAG、Wiki、生成逻辑和审核规则，但边界仍分散 | 明确四类资产：用户偏好Memory、项目事实State、公司知识Wiki、可执行流程Skill；禁止互相替代 | P0 |
| Skill渐进加载 | 当前规则和生成逻辑可能一次注入较多 | 建立L0目录摘要、L1技能正文、L2引用材料三级加载，只向当前步骤注入所需内容 | P0 |
| Skill写入审批 | 已有管理员增强和发布能力，但还不是统一候选变更流 | AI只生成增强候选；保存差异、依据和评测结果；管理员批准后发布新版本，支持拒绝和回滚 | P0 |
| 会话压缩与谱系 | 项目状态可恢复，但长对话压缩和父子会话关系不足 | 压缩前先固化项目事实和任务状态；保留最近对话及工具调用/结果对；摘要标记为历史参考；建立parent_session_id | P0 |
| Toolsets最小授权 | 工具有白名单，但主要按Agent静态配置 | 按场景建立“资料检索、测算、写作、审查、PPT、管理员”工具包；每次Run只挂载必要工具 | P0 |
| 统一运行回调 | 页面各自展示进度，事件格式未统一 | 建立Run事件总线：thinking、tool_start、tool_end、clarify、approval_required、step_complete、failed、completed | P1 |
| Profile隔离 | 已有用户和项目隔离，部门能力仍不足 | Profile映射为部门/业务类型工作空间，分别隔离模型策略、技能、知识范围和工具权限 | P1 |
| Session Search | 已有历史项目与RAG，但缺少受控的跨会话检索 | 只按user_id、department_id、project_id授权检索历史会话摘要，返回引用而非整段灌入上下文 | P1 |
| 主模型与辅助模型分链 | 已有Provider故障切换 | 把主推理、摘要压缩、OCR/视觉、网络提取分别配置独立模型链和预算，局部失败不拖垮主任务 | P1 |
| 子Agent隔离上下文 | 尚未形成正式多Agent机制 | 仅用于可并行的只读研究、资料分类和初审；公式计算、正式发布和最终结论仍由单一受控主流程负责 | P2 |
| OS级隔离 | 主要依赖应用权限和人工闸门 | 服务器部署时将文档解析、OCR、外部抓取等高风险工具放入受限Worker/容器，限制目录、网络、CPU和内存 | P0（部署前） |
| Doctor预检 | 已有零散Provider状态检查 | 增加统一启动体检：数据库、模型、向量库、OCR、地图、文件目录、队列、迁移版本和权限策略 | P1 |

### 3. 最值得本项目优先实现的“业务技能闭环”

Hermes把较长的操作经验沉淀为Skill，而不是把所有经验塞进长期Memory。这个思路与本项目“管理员逐节增强可研逻辑”高度契合，建议把它建设为正式闭环：

1. 用户在某一可研小节中上传资料、纠正AI、反复修改并形成满意内容。
2. 系统提取本次新增经验，但只生成`skill_candidate`，不得直接改正式生成规则。
3. 候选内容必须说明：适用业务类型、章节/小节、触发条件、所需材料、工具调用顺序、生成模板、核查规则、来源依据和不适用边界。
4. 系统展示“旧版本→候选版本”的逐字段差异，并用真实项目样例做离线回放评测。
5. 管理员可编辑、批准、拒绝；批准后产生不可变版本号，旧项目继续绑定原版本，新项目默认采用已发布新版本。
6. 新版本出现质量下降时可一键回滚，同时保留失败原因，防止AI日后重复提出同类错误增强。

建议最小数据结构：

- `agent_skills`：技能身份、业务类型、适用章节、状态和当前发布版本。
- `agent_skill_versions`：完整内容、来源、版本、创建人与发布时间。
- `agent_skill_candidates`：AI候选、触发会话、差异、依据、评测结果和审批状态。
- `agent_skill_bindings`：技能与工具、知识库、规则、表格模板及章节的关联。
- `agent_skill_evals`：候选版本在真实案例上的质量、数字一致性、引用覆盖率和人工修改率。

### 4. 上下文压缩必须遵守的四条不变量

Hermes的上下文压缩实现表明，企业Agent不能简单截断聊天记录。项目应建立以下不变量：

1. **先持久化再压缩**：项目确认事实、未完成步骤、人工锁定内容和审批状态先写入数据库。
2. **工具对不可拆分**：工具调用与对应结果必须一起保留或一起摘要，避免模型看到调用却看不到结果。
3. **最新指令优先**：压缩摘要只能作为历史参考，不能把旧任务重新变成当前任务；停止、撤销和改变方向必须立即覆盖旧摘要。
4. **建立会话谱系**：每次压缩形成子会话并保存父会话ID、压缩版本、摘要模型和覆盖的消息范围，便于审计和恢复。

### 5. 安全方面必须接受Hermes的关键结论

Hermes的安全说明明确指出：工具白名单、危险命令识别和人工确认只是降低误操作的启发式措施，不能替代操作系统隔离。对本项目意味着：

- 大模型无权直接执行任意Shell或访问任意本地文件。
- 文档解析、OCR、网页抓取和将来的MCP工具按风险放入独立Worker；只挂载任务需要的临时目录。
- 对外网络采用域名/地址白名单；数据库凭证按只读、业务写入、管理员分别配置。
- Session ID只是路由标识，不能作为授权凭证；每次恢复、审批和工具调用都重新核验用户、部门、项目和动作权限。
- 任何自动沉淀的Memory、Skill、Wiki或生成规则都必须经过内容扫描和人工发布，不允许模型自行进入正式生产口径。

### 6. 不建议照搬的Hermes能力

- 不引入面向个人代理的Telegram、Discord等多渠道Gateway，当前前台、后台和项目对话已经足够。
- 不开放通用终端、任意文件编辑和自修改代码能力。
- 不使用一个全局Memory文件服务多人；企业环境必须按用户、部门和项目隔离并保留审计。
- 不让AI自由创建、修改或删除正式Skill；只能生成待审批候选。
- 不因Hermes支持多Agent就立即拆成大量Agent。当前优先事项仍是Run/Step/Checkpoint、工具治理和评测，而不是增加角色数量。

### 7. 对原实施路线的调整

在原六阶段不变的基础上，增加以下准入要求：

- **第一阶段同时加入**：会话谱系、压缩前事实固化、统一Run事件总线。
- **第二阶段同时加入**：场景Toolsets、Profile隔离、Session ID非授权边界。
- **第三阶段同时加入**：Memory/State/Wiki/Skill四层上下文以及L0/L1/L2渐进加载。
- **第四阶段同时加入**：Skill候选评测、管理员差异审批和版本回滚指标。
- **第五阶段同时加入**：文档解析/OCR/网络抓取Worker的OS级隔离与统一Doctor体检。
- **第六阶段保持选择性**：只有长任务Checkpoint和真正可并行只读任务才引入LangGraph或子Agent。

吸收Hermes后，前三项建设顺序调整为：

1. **Run/Step/Checkpoint/Approval + 会话谱系与安全压缩**。
2. **统一工具网关 + 场景Toolsets + Profile/权限隔离**。
3. **Memory/State/Wiki/Skill分层 + Skill候选审批与评测闭环**。

这三项完成后，系统不只是“能调用工具”，而会形成可恢复、可学习、可审批、可回滚且不污染正式规则的企业Agent底座。

## 九、外部12维评分的低分项覆盖核查

外部评分将当前AgentCore评为约7.4/10，整体方向基本合理，但不同指标对本项目的重要性不相同。不能把Hermes或LangGraph的通用能力简单当成必须复制的产品清单。

| 维度 | 外部评分反映的问题 | 本方案是否覆盖 | 最终处理 |
|---|---|---|---|
| 架构设计 | 前端Agent循环、业务流程和运行时边界仍需拆分 | 已覆盖 | 服务端Run底座；业务编排、工具、上下文和界面分层 |
| Agent循环 | 有限轮ReAct已实现，但计划、反思、预算和恢复偏弱 | 已覆盖 | Step状态机、总耗时/成本/重复调用熔断、Checkpoint和人工中断 |
| 工具调用 | 已达到较好基础，仍缺企业治理 | 已覆盖 | 统一Schema、版本、权限、超时、重试、幂等、熔断和审计 |
| 多Agent | 当前接近单Agent | 有条件覆盖 | 只为只读研究、资料分类等真正可并行任务增加子Agent；公式和正式结论不拆 |
| 记忆与学习 | 有长期记忆但缺安全自我改进 | 重点补充 | Memory/State/Wiki/Skill分层；Skill候选、差异审批、评测、发布和回滚 |
| 知识/RAG | 当前是优势 | 已覆盖持续治理 | 保持证据追溯、版本效力、权限过滤和按步骤最小注入 |
| MCP/外部集成 | 有MCP方向但尚非统一企业接口 | 补充覆盖 | MCP只能作为工具网关适配器，不能绕过权限、审计和错误隔离 |
| 可视化与交互 | 当前是优势 | 已覆盖持续治理 | 统一Run事件、进度、澄清、审批、差异和恢复界面 |
| 部署难度 | 本地部署基础较好 | 已覆盖 | Doctor体检、容器/Worker隔离、队列、备份恢复和SLO |
| 代码质量 | 历史单文件较大、共享全局脚本风险仍存在 | 已覆盖 | 模块准入、前缀/IIFE、契约测试、小补丁和运行时拆分 |
| 社区活跃度 | 自研项目不具备公共社区 | 不按原指标追分 | 替换为内部生态成熟度：插件/Skill/Provider规范、文档、示例、兼容和负责人 |
| 业务适配度 | 当前是绝对优势 | 保持 | 白箱数值、可研逻辑、审查、证据与人工签发不因框架升级而削弱 |

核查结论：评分较低且真正影响企业应用的内容已全部进入本方案。唯一不直接追求的是“公共社区活跃度”和没有明确收益的多Agent数量；前者改为内部生态成熟度，后者坚持按业务必要性建设。

核心数据库结构、Node/Hono运行循环、工具网关、上下文压缩、Skill审批、MCP适配和测试代码骨架，另见同目录的《0826企业级Agent核心代码学习与实施蓝图.md》。
