## 一、先核清截图中的两个问题

### 1. CI并非“没有正式跑起来”，但还不是强制门禁

- `.github/workflows/ci.yml` 已在 `main` 分支和远端提交 `3b4ca31` 中。
- GitHub Actions 最近一次 `质量与发布门禁` 于2026-09-04运行成功，运行号33830573111。
- 工作流已经执行语法检查、Release Consistency、Golden定向回归和全仓测试。
- 但是远端 `main` 当前未启用Branch Protection。因此准确结论是：**CI已经自动运行，但直接推送仍可能绕开“必须通过CI才能进入main”的强制门禁。**

### 2. “74/13与165/14是同一个正式库”不成立，但单一事实源仍未完全统一

- 改造类 `gaibao`：Canonical JSON与Runtime Seed均为74条/13章，Baseline ID一致，Release Check的SHA-256一致性检查已通过。
- 出租类 `rent`：当前实际为137条/14章，并非截图所述165条；它是另一项目类型，API通过`projectType`独立加载，不能删除或拿74条改造规则替代。
- 真正缺口：改造类采用“Canonical JSON → 自动生成Runtime Seed”，出租类仍是“Excel → Runtime Seed”，尚未纳入同一Manifest、Hash和生成门禁。
- 正确处理不是删除出租规则文件，而是把出租类也迁移到Canonical JSON，并把两个项目类型登记到同一个规则清单和发布检查中。

## 二、统一评分方法

### 2.1 证据等级

|分数锚点|必须具备的证据|
|---:|---|
|0|能力不存在|
|20|只有设想、方案或文档|
|40|隔离原型，未进入正式主流程|
|60|已进入主流程，但闭环、异常态或兼容性不足|
|75|有行为测试、版本治理和可重复验证|
|85|具备权限、审计、失败恢复及相邻链路验证|
|95|多个真实项目、多人使用和生产指标持续验证|
|100|长期规模运行、独立复核，且没有未解释的重大边界|

评分上限：未进主流程≤59；无行为测试≤69；无版本/权限/审计≤84；无真实项目≤89；无多人、多项目、跨版本和持续运行证据≤94。方案文档本身不提高实现分。

### 2.2 三类结果必须分开

1. **能力覆盖平均分**：系统能做多少、闭环到什么程度。
2. **生产成熟度加权分**：权限、租户、CI、队列、可观测、SLO、灾备等是否能支撑企业运行。
3. **真实数据资产成熟度**：真实项目、经理修改、Golden/Holdout、预测与实际结果是否形成长期资产。

外部材料的“约92.8分”更接近功能覆盖观察值，不能直接替代生产成熟度和数据资产成熟度。

## 四、当前最值得做的提分清单

### P0：现在就能完成，且投入产出最高

1. **把出租类规则纳入Canonical单一事实源**
   - 从当前137条Runtime Seed生成并人工核对`data/report-logic-rent-v1.json`。
   - 扩展生成器，同时由rent/gaibao Canonical生成各自Runtime Seed。
   - 新增规则Manifest，记录项目类型、Canonical路径、生成物路径、规则数、章节数、Baseline ID和Hash。
   - Release Check按Manifest逐类验证，禁止手工修改生成物。
   - 定向测试验证两类项目互不串库、旧项目仍兼容。

2. **把“CI会跑”升级为“CI必须通过”**
   - 工作流依赖安装从`npm install`改为可重复的`npm ci`。
   - 保留push、pull_request和手动触发，上传Release Check与Golden摘要。
   - GitHub `main`开启Branch Protection，要求`quality-gate`成功后才能合并，限制直接推送。
   - 制造一条受控失败PR验证门禁，再关闭测试PR；不能只看绿色页面。

3. **建立Release Manifest**
   - 记录Commit、规则/表格/提示词版本、Migration版本、Golden结果、构建Hash和发布时间。
   - 发布前自动生成并校验；线上健康接口返回实际运行Manifest。
   - 页面管理员区能查看“当前运行版本”，避免本地、GitHub和线上版本混淆。

4. **补空数据库与重复迁移门禁**
   - CI分别验证从空库初始化、旧版本逐步升级、同一Migration重复执行。
   - 对表、索引、默认值和关键约束做结构快照。
   - 失败必须阻断Release Gate。

### P1：可以开始建设，但应拆成独立任务

5. **真实Golden/Holdout闭环**
   - 等经理意见整理完成后，把原始资料、AI初稿、经理修改、正式Word和差异标签绑定成一个Golden项目。
   - 经理确认项目作为Training；另选至少两个项目作为Holdout，禁止拿训练项目自证泛化。
   - 指标至少包括事实错误、漏项、数字勾稽、引用有效、结构命中和人工修改量。

6. **Evidence签发阻断**
   - 报告事实、数字和结论绑定Evidence ID、版本、时效与权限。
   - 关键结论没有合格证据时，只能标待补，不能进入正式签发。
   - Word和PPT导出共享同一Evidence引用。

7. **RBAC与项目成员基础版**
   - 先建Organization、Project Membership、Role、Permission、Data Scope最小模型。
   - 优先保护发布规则、回滚规则、修改参数、审批变更和机密导出五类高风险动作。
   - 每个拒绝与批准动作进入审计日志。

8. **任务队列与Checkpoint基础版**
   - 先迁移报告批量生成、长文档解析和PPT生成三类重任务。
   - 支持排队、限流、超时、重试、取消、断点恢复、幂等键和失败节点重跑。
   - 普通API不和重型AI任务共用无限并发池。

9. **统一可观测性与成本记录**
   - 为每个任务生成trace/task ID，记录项目、步骤、Provider、模型、耗时、重试、Token和成本。
   - 建立成功率、P95、Provider失败率、队列积压、Golden失败和预算消耗指标。
   - 告警必须指向具体项目和失败步骤，不能只显示`fetch failed`。

10. **SLO、备份恢复与容量基线**
    - 先定义当前阶段可兑现的可用性、P95、RPO和RTO。
    - 完成数据库备份恢复、对象存储版本恢复和Worker重试演练。
    - 将在线用户、普通API和重型AI Job分别压测，形成容量上限和扩容触发条件。

### P2：现在可设计，不宜靠本地代码虚假提分

- OA/SSO：需要集团身份源、组织字段和流程接口后实施。
- 多租户行级隔离：需要生产数据库策略、迁移和跨租户攻击测试。
- 百万文件：先完成对象存储和分层解析，再做真实规模压测；不能用少量夹具外推。
- 高可用：需要多实例、负载均衡、生产数据库和故障切换环境。
- 长期数据资产：必须依靠多个真实项目和数月后评价积累，不能靠生成模拟数据提分。

## 五、推荐执行顺序

```text
阶段1：rent/gaibao统一Canonical + Manifest + Release Check
  ↓
阶段2：npm ci + main分支保护 + 受控失败PR验证
  ↓
阶段3：空库/升级Migration门禁 + 运行版本可见
  ↓
阶段4：税务局Golden项目 + 独立Holdout + Evidence签发阻断
  ↓
阶段5：RBAC/租户基础 → Queue/Checkpoint → Observability/SLO
  ↓
阶段6：对象存储/统一搜索 → 容量压测 → 灾备切换 → OA桥接
```

下一项最合适直接开工的是阶段1。它不依赖经理意见，也不需要引入Redis、OA或生产数据库，能够真正补齐当前规则单一事实源的剩余缺口。
